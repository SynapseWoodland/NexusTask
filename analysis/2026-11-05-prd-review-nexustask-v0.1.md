## 四、深度评审：实质问题清单（按严重度）

### P0 —— 不改会在面试现场被问穿

**P0-1｜评测口径未定义，而这张表被 PRD 自己认定为"最硬的东西"**

§8 L269 原文："**这张表就是你面试时最硬的东西**"。但 §8 L268 的"成功率"从未定义：是"Agent 跑完没报错"（执行成功），还是"答案与标准 SQL 的结果一致"（结果正确）？FR-13 L191 的五个指标也都没定义判定规则；FR-02 L124 的"DAG 结构正确率 ≥85%（人工判定）"——人工判定的标注标准、标注人、标注一致性（双标一致率）全无。

后果链条：口径不定 → 成功率不可比 → §8 四组对比表不可信 → 简历数字不可信 → **JD 要求 5（定位执行失败/幻觉/工具异常）失去证据支撑**。而 PRD 的 §1.3 L52 硬约束（结构化通信）本就是为了可评测，评测口径却恰恰是最松的一环。

**修法**：补一张《评测指标定义表》，每指标四列——定义 / 判定方式（自动/人工）/ 判定样本 / 边界情况处理。例如"任务成功率 = 输出结果集与标准 SQL 结果集完全一致（数值容差 1e-6）的题目数 ÷ 总题数；执行报错计失败，重试后成功计成功"。

**P0-2｜FR-06 的"数字异常"检测没有可实现判据**

L160 原文："量级/分布校验、与历史值比对｜交叉校验（换口径重算）再决定是否输出"。三个问题：① **阈值未定义**（偏离历史均值多少触发？几个 σ？）；② **"历史值"从哪来**——评测集是自建静态数据集，没有"历史"序列，训练/推理前无历史可比；③ **误报代价不对称**——误判"异常"会触发重算并拉高 token 成本、直接压低 NFR-02 的 ≤¥0.5。

这张表是 NFR-01（成功率 ≥80%）能否达成的关键变量，而它现在是四个词。**它不可实现 → NFR-01 不可达成 → 整个评测章节失去地基。**

**修法**：给出具体判据，例如"结果数值超出该指标近 7 期历史均值 ±3σ 触发；无历史时（冷启动）跳过该检测，依赖另外三类失败检测；单次任务因该检测触发的重算上限 1 次"。同时把冷启动路径写进 FR-05 的状态机。

**P0-3｜"口径歧义"是整个 RAG 与 Critic 设计的立论基础，但被消解在数据准备阶段**

§2.2 L73 "天然有 RAG：指标口径必须检索，且检索错了 SQL 就错"；§6.3 L240 "自建才能保证'业务口径'有歧义可讲（退货率是按单还是按件？）"。**但 §6.3 L239 只说"字段语义写进 `metric_kb`"，而 §3 FR-03 L132 说"口径未命中必须拒绝执行"——如果 `metric_kb` 里"退货率"只有一个定义，歧义根本不存在，检索也就不会"检索错"。**

那么：歧义在哪？是在 metric_kb 里存两个候选口径（按单/按件）由系统选择？是由 FR-01 的反问澄清来解决？还是根本不存在歧义、§2.2 L73 是过度论证？三选一，必须选一个并写下来。**因为 FR-01 的澄清机制、FR-06 的口径校验、FR-04 的 metric_kb，三者都挂在这个假设上。**

**修法**：明确 metric_kb 支持**一对多候选口径 + 消歧策略**（用户澄清 > 上下文默认 > 拒答），并把"歧义消解"作为 FR-01 澄清触发器之一写进验收标准（20 条模糊问句中至少 5 条为口径歧义题）。

**P0-4｜工期口径冲突未消解，排期不可执行**

PRD L5 前提："6 周、每天 2–3 小时"。`analysis/2026-11-05-effort-estimate-12h-ai.md` 结论："6 周 × 2–3h/天 ≈ 84–126 小时，真实裸人力约 300 小时（+AI 后 139h）"，并给出 M 档 15–17 天（12h/天）。两份文件同在一个 `docs/`+`analysis/` 结构里，PRD 完全未引用这个估算，等于**排期建立在已被证伪的工时假设上**。

同时，§9 L284 "每周必须留一次可演示状态……做不完就砍 P1" 与 §11 L305 风险表"砍 P1：先砍四工作流切换"存在**内在矛盾**：砍掉四工作流 = 砍掉 FR-08 = §8 对比表从 4 列变 2 列 = 丢掉 JD 要求 3 的应答素材，而 §8 L269 恰恰说这张表是"最硬的东西"。**降级方案摧毁的是自己的核心卖点，PRD 没意识到这个矛盾。**

**修法**：把 PRD 的前提改为引用估算文档的 M/L 档结论（如"16 天 × 12h"），并把"砍四工作流"的降级方案从第一顺位移除，改成"砍 K8s → 砍前端单页 → 砍 P1 中的 SSE 增强"，保证 FR-08 与 FR-13 不在降级清单首位。

**P0-5｜状态机缺状态，FR-14 的 cancel 接口与 FR-10 的"降级返回部分结果"语义未闭合**

FR-05 L146-148 的状态图只有 `INIT / PLAN / RETRIEVE / EXECUTE / CRITIQUE / OUTPUT / REPLAN / FAILED`——**没有 CANCELLED，也没有 DEGRADED/PARTIAL**。但 FR-14 L196 提供了 `POST /tasks/{id}/cancel`，FR-10 L179 又要求"最后返回部分结果并标注'未完成'"。取消与降级是两件不同的事，现在都无处安放。同时 §6.2 L232 `task_step` 的"最终状态"字段也无枚举定义。

**修法**：状态机补 `CANCELLED` 与 `PARTIAL` 两态，给出状态转移表（当前态 × 事件 × 下一态 × 是否写 checkpoint），并在 `task`/`task_step` 表中显式列出状态枚举。

### P1 —— 影响专业度与追问深度

**P1-1｜NFR-04 "50 并发不降级"没有容量口径，等于把 JD 要求 4 降级成名词**

L208 "50 并发不降级；K8s HPA 按队列深度扩缩"。但一次任务不是一次 LLM 调用：Planner(≥1) + Executor(每步 1 次工具/可能多轮) + Critic(≥1) + 可能的 REPLAN，**单任务乐观估计 8–15 次模型调用**，50 并发即每分钟 400–750 次调用量。供应商 RPM/TPM 配额、日内限流窗口、是否需要多 Key/多供应商降级、限流时如何计入 FR-10 的"降级"链——全部空白。JD 要求 4 原文是"有构建**高并发、可扩展 AI 服务**经验者优先"，这正是加分位，缺口必须补。

**修法**：给出单任务调用次数上界估算、目标 RPM/QPS、以及限流触发的降级路径（队列积压 → 延长 P95 → 触发 NFR-03 告警），并明确"50 并发不降级"的判定是"成功率不下降"还是"P95 不上升"。

**P1-2｜FR-11 的失败分类只有四类，缺 JD 要求 5 明写的"工具调用异常"**

L184 验收："5 分钟内能定位到是'规划错/检索错/工具错/模型幻觉'中的哪一类"——四类里"工具错"是笼统的。JD 原文要求独立定位"**执行失败 / 幻觉 / 工具调用异常**"。建议把失败分类扩为六类并给出可自动判定的信号来源：规划错（DAG 结构校验失败）、检索错（metric_kb 未命中/低相似度）、工具参数错（schema 校验失败）、工具执行错（SQL 异常/超时）、幻觉（输出引用未命中口径）、预算超限（token/步数/时长）。每类给出**自动判定规则**，否则"5 分钟内定位"依赖人肉读 trace，与 FR-11 的自动化意图相悖。

**P1-3｜P0 依赖没有降级路径**

Milvus 是 P0 依赖（FR-04、FR-03 的 schema_search/metric_lookup 全建在它上面），§7 L253 虽写"数据量 < 10 万可先用 pgvector"，但被框定为"技术选型换回条件"，没有进入 §11 风险降级表。而估算文档 §三 明确指出 Milvus standalone 的 etcd+minio 版本兼容"是坑"。P0 依赖不可用 = 系统不可运行，必须有降级路径。**修法**：§11 补一行——"Milvus 部署失败 → 降级 pgvector（单集合 + 全文检索），保留接口不变，W1 内验证一次降级链路"。

**P1-4｜demo 交付物依赖实时 API，无离线回放方案**

§10 L292 交付物含"3 分钟 demo 录屏（流式进度 + 一次失败的自我修复）"。§11 L308 的"模型 API 不稳定 → Ollama 本地兜底"能解决可用性，但**录屏现场 50 并发 + 反思重试链路的稳定性**没有保障，且失败重试恰恰是最容易卡死的一段。**修法**：录屏基于 Langfuse trace 回放（trace 已在 FR-11 中），"一次失败的自我修复"用回放展示而非实时触发，并保留一条实时录制的备用版本。

## 五、这份 PRD 做对了什么

1. **§7 技术选型表是整份文档最成熟的部分**（L246-255）。每项选型都给了「分工边界 + 换回触发条件」，且**不贬低替代方案**——"不用 LlamaIndex"写的是"它的分工是纯 RAG 索引与检索引擎，本项目检索要参与决策"，并给出"文档量涨到需要多索引结构时整体替换"。这正是面试官"为什么不用 X"的标准答法，且与同仓库 gap 分析文档 §七 口径一致。
2. **每条 FR 都带可判定的验收阈值**（L120/L124/L137/L142/L151/L163/L168/L176/L180/L184/L193/L197）。多数 PRD 只写"要支持 XX"，这份写"20 条模糊问句澄清触发率 ≥80%，误澄清率 ≤10%"——这直接救回了模块 3 的 1.3 分。
3. **§1.3 L52 的硬约束（多 Agent 只传结构化产物、禁止自由对话）**是真正的设计决策而非口号：它把"多 Agent 自由协商"的失控风险在架构层前置消除，同时保住了可评测性，并且 §11 L309 把"多 Agent 写失控"列为中概率风险并指向同一条约束——**设计决策与风险表闭环**，这一点很多 PRD 做不到。
4. **§2.4 "明确不做"五条**（L84-90）：不写 DML/DDL、不接第三方数据源、不做自由对话多 Agent、不做微调、不做产品级前端。范围收得住，是成熟度的标志。
5. **§11 风险表给了概率 + 具体降级动作**，且原则明确（"砍 P1，不砍 P0"，L284 / L305）。
6. **§2.2 的三个"天然"论证**思路正确——先证明场景自带 ground truth、自带反思触发条件、自带 RAG 必要性，再谈系统设计，避免了"先选技术再找场景"。**问题不在思路，在数据支撑（P0-1/P0-3），不在框架。**
