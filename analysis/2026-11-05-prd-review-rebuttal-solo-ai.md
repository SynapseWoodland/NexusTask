## 二、必须认的（评审说对了，而且是设计问题不是文档问题）

| 编号 | 问题 | 为什么致命 |
|---|---|---|
| D1 | **"成功率"未定义**：是"任务跑完没报错"还是"结果与标准 SQL 一致" | 这一条决定 §8 对比表和简历三个数字是否可信。JD 要求 5 全靠它撑 |
| D2 | **FR-06"与历史值比对"在静态数据集上不成立** | 自建数据集没有"近 7 期"序列，冷启动时该检测无法触发。反射闭环的三条腿瘸了一条 |
| D3 | **口径歧义自相矛盾** | §2.2 说"RAG 天然必要因为口径有歧义"，但 §6.3 只让 `metric_kb` 存一条口径、FR-03 还要求"未命中必须拒绝执行"。**若只有一条口径，歧义不存在，RAG 的立论塌了** |
| D4 | **状态机缺 CANCELLED / PARTIAL** | FR-14 有 cancel 接口、FR-10 有"返回部分结果"，状态机里都没有落点 |
| D5 | **降级清单第一项砍四工作流** | 砍掉 FR-08 = 对比表从 4 列变 2 列 = 丢掉 JD 要求 3 的应答素材。**降级方案摧毁了核心卖点** |
| D6 | **威胁模型错位** | 我防的是"知识库内容注入"（自建数据，风险≈0），真正该防的是用户问句注入、审计表落敏感金额、业务问句发给外部模型 |

这六条不是"PRD 格式问题"，是**面试官会当场问穿的东西**。D1 和 D3 尤其致命——它们动摇的是整个项目的立论。

## 三、不认的（对单人项目是模板税，别为它写东西）

| 编号 | 评审要求 | 为什么不认 |
|---|---|---|
| R1 | 补设计师 / PM / 技术负责人 / 测试主R / 需求提出人 / tapd | 单人项目无对应角色。**正确做法是写一行"单人自研，上述角色均由本人承担"**，而不是造人名 |
| R2 | 补灰度方案 + 回滚预案 | 无发布即无灰度。一行"无需线上灰度，A/B/C/D 离线对比为等效灰度"即闭合 |
| R3 | 为 50 并发补 RPM/TPM 配额与多 Key 降级 | **问题不在容量工程，在声称过配**。个人项目不会有 50 个并发真实用户。应把声称降到"20 并发 + 无任务串号"，验收改为"成功率不下降"，而不是加班做限流分层 |
| R4 | 补"月均影响 X 万用户、转化率下降 Y%" | **个人项目拿不出这个数，编造比缺失更糟**。正确做法是改成"参考场景 + 假设参数"并显式标注为假设 |
| R5 | 模块 1 计 0 分导致整体不合格 | 已计入模板税，不影响决策 |

## 五、比分数更该注意的一件事：工期前提

PRD 写的是 **6 周 × 2–3h/天 ≈ 84–126h**；工时估算文档的结论是 **15–17 天 × 12h ≈ 139h**。

这两个数不是"谁错了"，是**两个不同的投入假设**，只能二选一：

- 若真实可投入是 **2–3h/天**：6 周只有 84–126h，PRD 必须降到 **S 档（8–10 天 × 12h ≈ 100h）**，砍掉四工作流 + 50 题评测，否则排期不可执行。
- 若真实可投入是 **12h/天**：15–17 天完成 M 档，6 周绰绰有余，此时应反过来把"6 周"改成"3 周 + 1 周缓冲 + 2 周理解预算"。

**这个前提不钉死，PRD 里的所有周次都是装饰。** 评审 P0-4 指出这一点是对的，只是它归因为"文档冲突"，实际是"决策未做"。

## 六、一句话

评审方法论没问题，但它把这当成一份要走设计/测试/灰度流程的公司立项 PRD 来打，所以 4.4 里有 1.6 分是模板税；扣掉模板税后真实内容分约 5.5–6.0，差距集中在**评测口径（D1）、口径歧义（D3）、异常判据（D2）三个设计洞**——这三条恰好都是面试官必问处，值得花 2.5 小时补，剩下的模板项用一行标注闭合即可。
