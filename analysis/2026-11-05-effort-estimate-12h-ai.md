# NexusTask 工期估算：1 人 + AI，每天 12 小时

> 日期：2026-11-05｜输入：`docs/PRD-nexustask-v0.1.md` v0.1｜仓库现状：空仓（仅 docs/ 与 analysis/）
> 估算基准：一人；12h/天为**纯工作时间**（不含吃饭休息，不含等待 API 的空转）；AI 形态为当前主流 Coding Agent（能读写全仓、跑命令、自我验证），**不是**无人值守的多 Agent 长跑。

---

## 一、结论先行

| 范围档位 | 内容 | 需要天数（12h/天） | 日历时间 |
|---|---|---|---|
| **S｜演示最小闭环** | 单指标 + 对比问句跑通、状态机、反思、一个单页、审计表 | **8–10 天** | 10–12 天 |
| **M｜PRD 全文照做**（推荐） | S + 四工作流切换 + 50 题评测报告 + 成本预算 + Langfuse + Docker Compose | **15–17 天** | 2.5–3 周 |
| **L｜PRD 全文 + 真压测** | M + K8s HPA 实跑 50 并发 + 演示视频打磨 + 简历数字回填 | **20–23 天** | 3.5–4 周 |

**一句话**：如果按 PRD 所有验收标准真跑出数字，**两周半到三周**；只求能演示能追问，**10 天内**；想把 K8s 和 80% 成功率都做实，**准备 20 天以上**。

---

## 二、为什么不是 PRD 里说的 6 周

PRD 的 6 周 × 2–3h/天 ≈ **84–126 小时**。按 PRD 每条验收标准逐项拆，真实裸人力约 **300 小时**（见下表），差 3 倍。

原因不是 PRD 写错了，而是那 105 小时的排期暗含"薄切片"假设：每周交付一个能演示的切片，而不是把每条验收指标都做实。**"能演示"和"验收指标达标"是两件事**，后者才是时间黑洞。

## 三、工作量拆解（裸人力 → AI 加持）

| # | 模块 | 裸人力(h) | +AI(h) | AI 增益 | 备注 |
|---|---|---|---|---|---|
| 1 | 自建数据集 10 表 50 万行 + metric_kb 口径 | 14 | 7 | 2.0x | 表结构/口径定义是**人的决策**，AI 只写脚本 |
| 2 | Docker Compose（MySQL/Redis/**Milvus**/Langfuse） | 6 | 3 | 2.0x | Milvus standalone 依赖 etcd+minio，版本兼容坑 |
| 3 | FastAPI 服务层（4 接口 + 幂等 + SSE） | 16 | 7 | 2.3x | 你有 Java 后端底子，这块判断力强 |
| 4 | LangGraph 状态机 + Redis checkpoint + 中断续跑 | 20 | 10 | 2.0x | 恢复语义有暗坑，AI 写的容易"看似对" |

| 8 | 三角色多 Agent（结构化通信） | 12 | 5 | 2.4x | 有硬约束，可控 |
| 9 | 四工作流可切换（FC / ReAct / P&E / MA） | 24 | 12 | 2.0x | 每个模式一套循环 + 统一接口 |
| 10 | 长期记忆（task_template_kb 复用） | 10 | 5 | 2.0x | 相似任务命中降步数，得测 |
| 11 | 成本预算 + 审计表 + Langfuse | 18 | 7 | 2.6x | 样板代码多，AI 最擅长 |
| 12 | 安全（只读/白名单/注入防护/脱敏） | 8 | 3 | 2.7x | 规则化，AI 写得好 |
| 13 | 前端单页 + SSE 进度 | 8 | 3 | 2.7x | 声明"非产品级" |
| 14 | **50 题评测集 + 人工标准 SQL** | 28 | 12 | 2.3x | AI 起草，**你必须逐条验 SQL 对错** |
| 15 | 评测 harness（四模式 × 50 题自动跑） | 10 | 4 | 2.5x | |
| 16 | **调优到成功率 ≥ 80%** | 35 | 18 | 1.9x | 最大不确定性，串行等待 |
| 17 | K8s manifests + HPA + 50 并发压测 | 12 | 5 | 2.4x | 本地 K8s 是时间黑洞 |
| 18 | README + 架构图 + 3 分钟 demo 录屏 | 10 | 4 | 2.5x | 录屏要重录，观感不可 AI 代劳 |
| 19 | 集成胶水 + 联调返工 | 20 | 10 | 2.0x | 老手都低估这一项 |
| | **合计** | **299** | **139** | **≈2.15x** | |

**139 小时 ÷ 12 小时 = 11.6 个"纯满产天"**。但 12h/天不可能 100% 满产：

- 等人思考、等模型出活、等 API 重试 ≈ 20–25% 损耗
- 状态切换（写代码 ↔ 跑评测 ↔ 看 trace）每天至少 1h
- 修 AI 引入的"看似对"的 bug，返工率约 15%

按**有效产出 8.5–9 h/天**折算，139h → **15–16 天**。这就是 M 档 15–17 天的来源。

## 四、逐日排期（M 档，16 天）

| 天 | 任务 | 当天结束必须能演示什么 |
|---|---|---|
| D1 | 数据集生成脚本 + metric_kb 初版 + Docker Compose 起 MySQL/Redis/Milvus | 库里能查出数、Milvus 能检索到口径 |
| D2 | FastAPI 骨架 + 工具注册表 + 5 个工具（含 SQL 安全约束） | 一条单指标问句端到端出数（无状态机，先直连） |
| D3 | LangGraph 状态机 + Redis checkpoint + 续跑 | 杀进程后能从断点恢复 |
| D4 | RAG 入链路（schema_search / metric_lookup）+ 口径未命中拒答 | 口径错时能拒绝执行并说明原因 |
| D5 | Planner DAG（含入参来源、验收条件、重试预算） | 多步问句能输出 DAG 并被执行 |
| D6 | Critic 四类失败 + REPLAN 循环 | 演示"SQL 写错 → 自动重写成功" |
| D7 | 三角色结构化协作 + trace 按角色回放 | 一次执行能按 Planner/Executor/Critic 回放 |
| D8 | 四工作流开关（FC / ReAct / P&E / MA） | 同一问题能切四种模式跑 |
| D9 | 长期记忆复用 + 预算控制（步数/token/时长） | 相似任务步数下降、超预算降级 |
| D10 | SSE 流式 + 前端单页 + 审计表写入 | 页面能看到逐步进度 |
| D11 | Langfuse 接入 + 失败分类定位 | 任取一次失败执行，5 分钟内定位类目 |
| D12 | 50 题评测集（四档比例）+ 人工校验标准 SQL | 50 题全部有可执行标准 SQL |
| D13 | 评测 harness + 首轮四模式跑分 | 出第一张对比表（哪怕很难看） |
| D14 | 按失败类型定位 → 调 prompt / 补规则 | 成功率进到 60–70% |
| D15 | 继续调优 + 修边角 bug | 成功率 ≥ 80%，成本 ≤ ¥0.5 |
| D16 | README + 架构图 + demo 录屏 + 简历数字回填 + 缓冲 | 仓库可一键启动、可对外展示 |

> 硬性节奏：**每天收工前必须有一个可演示状态**。做不完就砍 P1，别把 P0 拖成半成品——这个原则 PRD 里有，执行时最容易破。

## 五、AI 帮不上多少的 4 个瓶颈（决定你能不能压到 12 天）

1. **评测集的标准 SQL**：AI 能起草 50 条，但"这条 SQL 是不是业务正确"只有你能判。这是**串行人工**，AI 最多省 40%。
2. **调优到 80% 成功率**：非确定性系统，只能"改一版 → 跑 50 题 → 看失败分布 → 再改"。每轮 20–40 分钟，20 轮就是一天。AI 能读 trace、提假设，但**不能替你跑完这个循环**。
3. **Milvus / checkpoint 恢复语义**：AI 写出来的"看起来能跑"，但 checkpoint 恢复在边界情况（节点中途挂、消息半写）常出问题，必须你读源码级别的理解。
4. **本地 K8s HPA 实压测**：这不是代码问题，是环境和时间问题。建议真要用就放最后，且允许降级到 Docker Compose。

## 六、想压到 10 天以内怎么砍

按"面试冲击力 / 工时"排序，优先砍后两项：

| 砍什么 | 省工时 | 面试损失 | 替代说法 |
|---|---|---|---|
| K8s → Docker Compose | 5h | 小 | "服务无状态、可水平扩展，compose 验证过 50 并发" |
| 四工作流 → 只做 ReAct + P&E | 8h | 中 | "对比表两列，讲清差异，比四列都薄更好" |
| 前端单页 → CLI + SSE 日志 | 3h | 小 | demo 录屏用终端也够 |
| 评测集 50 → 30 题 | 6h | 中 | 四档比例不变，样本量说明局限 |
| **不能砍**：状态机、Critic、评测对比表 | — | 全盘 | 这三项是 JD 命门 |

砍完约 **139 − 22 = 117h → 10 天左右**。

---

## 七、一个必须提醒的点

12h/天 × 2.5 周的产出，你会有一批"AI 写的、你只读过一遍"的代码。面试官一定会挑 DAG 结构、checkpoint 恢复、Critic 阈值追问——**被问穿比做不完更致命**。

建议每天留 **1–1.5h 的"理解预算"**：不看 AI 的总结，只读当天新增代码，并在 `docs/decisions/` 下写 3 行"为什么这样做、换什么条件会改"。这 1.5h 不计入上面的 139h，是额外成本——但它是这个项目能拿去面试的前提。

折算后：**M 档真实日历时间 17–19 天**。如果你同意这个理解预算，估算表里的"15–17 天纯产出"才成立。
