## 0. 本文档替你做的三个决定

### 决定一：砍掉 Java 侧，全力做 Agent

**为什么砍**（三条，按权重）：

| # | 理由 |
|---|---|
| 1 | **JD 是 Python 中心**。目标 JD 与小红书面经里，没有任何一条考"Python Agent 对接老 Java"。考的是幂等/重复扣费、多 Agent 必要性、上下文管理、评测、并发、架构深度 |
| 2 | **6 周的边际收益为负**。Java 侧吃掉 3–4 天，还要维护双栈；而它换来的"集成故事"在面试里要先解释"这系统是我自己写的"，可信度天然打折 |
| 3 | **失败点不在广度**。面经里真实挂人理由是"复杂系统架构设计能力不足""说不清为什么要多 Agent"，不是"没对接过遗留系统" |

**砍掉本身就值得讲**：被问"为什么不做个 Java 系统"时，答"我评估过双栈，六周里它的边际收益低于把评测做深，所以砍了"——这比多一个半成品系统更能证明判断力。

### 决定二：场景定为「电商交易资金侧」，不是 SaaS 订阅

| 保留 | 去掉 |
|---|---|
| 订单、支付、退款、结算、对账、商家、商品、渠道、活动、成本 | 订阅套餐、坐席、风控评分系统 |

理由：**它同时是电商，也是你的老本行**。而且退款/对账天然带出幂等、重复扣费、金额精度这些高频考点（小红书 2026-09 面经原题就是"接口幂等与重复扣费"）。

### 决定三：把"失败归因"做成头牌，不是附属章节

普通作品集讲 happy path；这个项目讲 **"失败能不能说清楚"**。这是 JD 要求 5 的原文，也是面经里被追问最狠的地方。

## 1. 定位与差异化

**一句话**：用户用自然语言问经营数据，系统澄清口径歧义、拆解任务、生成只读 SQL、校验结果、必要重算，并**把每一次失败归到六类中的一类**，全过程可回放、可算成本。

**与"烂大街作品集"的对照**：

| 普通作品集 | 本项目 |
|---|---|
| RAG 问答 + 3 个工具 | **50 题标准答案**的成功率 |
| "我用了 LangGraph" | **同一 50 题、四种工作流**的对比表 |
| "成功率 80%" 说不清口径 | 六项指标定义表 + contested 剔除规则 |
| 失败就重试 | **六类失败自动归因** + 修复率 |
| 单 Agent | 多 Agent 的**必要性**能被追问三层 |
| 只讲能跑通 | 讲**为什么不那样做**（增删每个模块都有理由） |

**竞争力判断**：这个方向能打。原因不是技术新，而是**可量化 + 可辩护**——两个面试里最稀缺的东西。

## 2. 场景与数据

**用户**：电商运营、财务、商家运营。
**问题**：
1. 临时取数排队，平均等 1–2 天
2. 同一指标多个口径（GMV 含不含税/含不含取消单；退款率按单/按金额；客单价按支付/按下单）
3. BI 只能回答已定义好的问题，回答不了"为什么涨了"

**数据集（10 表，约 50 万行，脚本生成）**：
`merchant` / `product` / `category` / `order` / `order_item` / `payment` / `refund` / `settlement` / `channel` / `campaign`

**三组口径歧义**（`metric_kb` 各存 ≥2 条候选）：
| 指标 | 争点 | 结果差异 |
|---|---|---|
| GMV | 含税/不含税；含不含取消单；含不含运费 | 5–15% |
| 退款率 | 按单/按金额；是否含售后期 | 可差 1 倍 |
| 客单价 | 按支付金额/按下单金额；是否含退款 | 10%+ |

**为什么歧义必须存在**：它改变 SQL 的聚合粒度（`SUM` vs `COUNT(DISTINCT)`），检索错必然结果错。RAG 是链路必经，不是装饰。

**PII 声明**：无姓名、手机号、地址、证件号；商家为虚构企业名。

## 3. 架构

```
接入层   FastAPI（异步 + 幂等 + SSE）
编排层   LangGraph 10 态状态机（含 CANCELLED / PARTIAL）
角色层   Planner / Executor / Critic（只传结构化产物，禁止自由对话）
能力层   工具注册表：4 个只读 SQL 工具 + sandbox_calc + chart_render + create_ticket（幂等写）
记忆层   Redis（会话 + checkpoint）｜ Milvus（metric_kb / task_template_kb）
数据层   MySQL（只读业务 + 审计表）
观测层   Langfuse + audit_log + 失败归因看板
```

**只保留一个写操作**：`create_ticket`（创建分析工单，幂等键去重）。用途不是业务闭环，而是给"幂等/重复提交"一个可演示的载体——面经原题。

## 5. 评测（项目的核心资产）

### 5.1 题库四档（50 题）

| 档 | 题量 | 内容 |
|---|---|---|
| A 单指标 | 12 | 需消歧的单步查询 |
| B 对比 | 12 | 多维聚合 |
| C 归因 | 14 | 多步下钻，需 2+ 工具 |
| D 拒答与边界 | 12 | 越权、无数据、口径不可消解、超出数据范围 |

### 5.2 指标（六项 + 定义）

| 指标 | 定义 | 门限 |
|---|---|---|
| 任务成功率 | 结果集与标准 SQL 一致（行序无关、键对齐、容差 1e-6、字符串去空格） | ≥ 80% |
| 首轮 SQL 正确率 | 第一次生成即通过校验且结果正确 | ≥ 65% |
| 消歧正确率 | 人工判定所选口径符合题意 | ≥ 90% |
| 平均步数 | 从 PLAN 到 OUTPUT 的节点数 | ≤ 6 |
| 单任务成本 | token 折算人民币 | ≤ ¥0.5 |
| P95 延迟 | 不含人工澄清等待 | < 10s |

**contested 规则**：标准 SQL 本身存疑的题标 `contested`，从分母剔除并单独报告数量。

### 5.3 四模式对比

同一 50 题跑 FC / ReAct / P&E / MA，输出成功率、步数、成本、P95、失败分布。**先把预期写下来再被数据推翻**：FC 快但多步弱；P&E 稳但首轮贵；MA 最好但最慢。

## 7. 面试：三张王牌 + 六个必答

### 三张王牌

| 王牌 | 一句话 |
|---|---|
| 一个真数字 | 50 题标准答案、六项指标定义、contested 剔除规则，随时可复算 |
| 一张对比表 | 同题四工作流，成功率/步数/成本/P95 四列 |
| 一个失败看板 | 六类失败自动归因，能说清"它为什么错" |

### 六个必答（提前背）

1. **为什么要多 Agent？** 不是为了多而多：规划、执行、校验的**上下文与失败模式不同**，拆开后每层可单测、可回放；合并成一个 Agent，Critic 的判定会被执行上下文污染。
2. **成功率怎么算？** 结果集一致，行序无关、键对齐、容差 1e-6；争议题剔除并单独报告。
3. **怎么定位失败？** 六类，每类有自动判定信号，不靠人肉读 trace。
4. **幂等怎么做？** 客户端幂等键 + 结果表 + 处理中状态，同键不同参报错。
5. **上下文怎么管？** 分层：任务态常驻、检索结果按需、工具返回摘要化、历史按模板压缩。
6. **和 BI 的区别？** BI 回答已定义好的问题；这里要处理口径消歧、多步下钻、结果自检三件事。

### 被问到 Java / 集成时

不主动提。若被问，答："我评估过 Java 双栈，六周里它的边际收益低于把评测做深，所以砍了。我的 Java 底子在计费/风控业务上，项目里用不上就不硬塞。"——**砍掉一个方案，比多做一个半成品更能证明判断力。**
