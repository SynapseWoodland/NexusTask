# 第一部分：ToT 推演记录

## 1.1 先定评价函数（不然选型就是拍脑袋）

| 维度 | 权重 | 为什么是这个权重 |
|---|---|---|
| JD 覆盖度 | 30% | 项目的唯一目的是拿这个岗，覆盖率就是命中率 |
| 可量化性 | 15% | 全篇没数字会被判成 demo，这是上一轮分析的最大硬伤 |
| 可演示性 | 15% | 面试现场 3 分钟要能讲明白、能跑出结果 |
| 6 周可完成 | 20% | 做不完的项目等于没做，权重必须高于"差异化" |
| 差异化 | 10% | 避免和"文档问答/客服机器人"撞车，但不是核心 |
| 数据与外部风险 | 10% | 造不出数据、依赖的 API 挂了，项目直接死 |

## 1.2 第一层：项目选题，展开 6 支

| 分支 | 选题 | 覆盖 | 量化 | 演示 | 6周 | 差异化 | 风险 | 加权 |
|---|---|---|---|---|---|---|---|---|
| B1 | 企业知识库问答（RAG） | 2.5 | 3.0 | 5.0 | 5.0 | 1.0 | 4.0 | **3.45** |
| B2 | 客服工单处理 Agent | 3.0 | 3.5 | 4.0 | 4.0 | 2.0 | 3.5 | **3.38** |
| B3 | 通用任务编排平台（原设定） | 4.5 | 2.0 | 2.5 | 2.0 | 4.0 | 2.5 | **3.08** |
| B4 | 数据分析 Agent（NL2SQL + 报表） | 4.0 | 4.5 | 5.0 | 4.0 | 3.5 | 3.5 | **4.13** |
| B5 | 运维告警根因分析 Agent | 4.5 | 2.5 | 3.0 | 2.5 | 4.5 | 2.0 | **3.33** |
| B6 | 代码库理解与修复 Agent | 4.0 | 3.0 | 3.5 | 1.5 | 5.0 | 1.5 | **3.13** |

**逐支剪枝理由**

- **B1 砍掉**：只覆盖 JD 加分项 2，职责 1 的"规划、反思"、职责 2 的"任务分解引擎、决策引擎"几乎用不上，多 Agent 也用不上。而且这是最烂大街的题，面试官一天看八个。
- **B2 砍掉**：业务味重、Agent 深度浅，反思闭环做不出来，容易变成"带 if-else 的工单分类器"。
- **B3 砍掉（但保留其架构叙事）**：原设定"通用任务枢纽"架构最对 JD，但"通用"意味着没有具体业务，demo 会空——你没法演示一个"什么都能干"的系统。它的架构层可以留，场景层必须收敛。
- **B5 砍掉**：差异化最高，但告警数据造假一眼被看穿。面试官必问"数据哪来的"，答"我造的"会连带把整个项目的可信度打掉。
- **B6 砍掉**：难度和 6 周严重冲突，评测集也难建，属于"做不完"的典型。
- **B4 保留为备选**：各项均衡，唯一问题是丢了"平台/枢纽"的架构叙事，职责 1 的"整体架构设计"讲起来弱一点。

## 1.3 第二层：把 B3 的架构 × B4 的场景合并，再展开 3 条技术路线

这是 ToT 的关键一步——不是"选一个分支"，而是发现 B3 和 B4 **冲突在场景层、互补在架构层**，可以合并成一支：**平台化架构 + 单一垂直场景落地（一横一纵）**。

| 分支 | 路线 | 优点 | 致命问题 |
|---|---|---|---|
| L2-A | 单 Agent + ReAct 循环 | 一周能写完 | JD 明确要"状态机与决策引擎"，这条完全交不出 |
| L2-B | LangGraph 状态机 + 单 Agent 节点 | 状态机覆盖到位，可 checkpoint 容错 | "多 Agent 协作"只能靠讲故事，追问就露馅 |
| L2-C | LangGraph 状态机做骨架 + 多角色 Agent 做节点 | 职责 1/2/3 全覆盖，且可控 | 容易写成"多 Agent 自由对话"，不可控、难评测 |

**选 L2-C，但加一条硬约束**：多 Agent 之间**不允许自由对话协商**，只能通过状态机传递结构化产物（任务 DAG、SQL、校验结论）。这样既拿到 Multi-Agent 的覆盖，又保住可评测性。这条约束本身就是面试加分项——说明你知道多 Agent 的自由对话在生产里是失控源。

## 1.4 收敛结论

> **NexusTask = 面向经营数据分析的任务执行 Agent**
> 架构层讲"任务枢纽"（平台/编排），场景层只做"经营数据问答与报表生成"一件事。

它赢在：**用 B3 的架构叙事拿 JD 职责 1/2/3，用 B4 的场景拿量化指标和 demo 效果，用你自己的后端背景拿工程深度。**

# 第二部分：产品定义

## 2.1 一句话

用户用自然语言问经营数据（"上个月华东区退货率最高的三个品类是什么，出个表"），系统自动拆解任务、检索指标口径、生成并执行只读 SQL、校验结果、渲染报表，全过程可观测、可回放、可算成本。

## 2.2 为什么这个场景能撑起 JD（场景自带的三个"天然"）

1. **天然有反思**：SQL 报错、结果为空、数字量级异常——三种失败都能自动检测并触发重试，不需要编造反思场景。
2. **天然有 ground truth**：自建数据集上每条问题都能人工写出标准 SQL，成功率可以真算，不是"我觉得还行"。
3. **天然有 RAG**：指标口径（"退货率"到底怎么算）和表结构必须检索，且检索错了 SQL 就错——RAG 不是装饰品，是链路必经环节。

## 2.3 目标用户与核心场景

| 角色 | 场景 | 输入 | 期望输出 |
|---|---|---|---|
| 运营 | 单指标查询 | "上周华东区 GMV" | 数字 + 口径说明 + 数据来源 |
| 运营 | 对比分析 | "本月和上月各品类退货率对比" | 表格 + 趋势图 + 一句结论 |
| 管理者 | 归因 | "为什么 10 月退款率涨了" | 多维下钻 + 归因假设 + 证据 |
| 管理者 | 报表 | "生成周报，导出 Excel" | 文件 + 执行摘要 |

## 2.4 明确不做（范围边界，面试时主动讲）

- 不做写入类操作（只读 SQL，无 DML/DDL）
- 不做通用 BI 平台（不接第三方数据源，只连自建数据集）
- 不做自由对话的多 Agent（见 1.3 硬约束）
- 不做模型微调（JD 全文没提训练，别跑偏）
- 不做前端产品级页面（一个能跑通的单页 + SSE 流式即可）

# 第四部分：功能需求

优先级：**P0 = 不做就不成立**，P1 = 面试追问必到，P2 = 有余力再加。

## FR-01 任务接入（P0）
自然语言 → 结构化任务单：`{意图类型, 指标, 维度, 时间范围, 过滤条件, 输出形态}`。
解析失败必须**反问澄清**而不是猜——这是"任务分解引擎"的入口，面试会问"用户说得模糊怎么办"。
**验收**：20 条模糊问句，澄清触发率 ≥ 80%，误澄清率 ≤ 10%。

## FR-02 任务分解引擎 Planner（P0）
输出**有依赖关系的步骤 DAG**，每步含：动作、工具、入参来源（常量/上游输出）、验收条件、预算（最多几次重试）。
**验收**：给定 20 条多步问题，DAG 结构正确率 ≥ 85%（人工判定）。

## FR-03 工具集成层（P0）
统一注册表，每个工具声明 JSON Schema（参数、返回、超时、幂等性、成本权重）。P0 工具 5 个：

| 工具 | 作用 | 关键约束 |
|---|---|---|
| `schema_search` | 检索表/字段语义 | 走 Milvus |
| `metric_lookup` | 检索指标口径 | 走 Milvus，口径未命中必须拒绝执行 |
| `sql_execute` | 只读执行 | 只允许 SELECT；表白名单；强制 LIMIT；30s 超时 |
| `python_calc` | 二次计算（同环比、占比） | 沙箱、禁止 IO |
| `chart_render` | 出图 | 输入必须是结构化数据 |

**验收**：新增一个工具不改编排代码，只加注册项。

## FR-04 长短期记忆（P0）
- **短期**：会话内上下文 + 当前任务 DAG 状态，落 Redis（带 TTL），支持中断续跑。
- **长期**：Milvus 两个集合——`metric_kb`（指标口径）、`task_template_kb`（历史成功任务的可复用 DAG）。
**验收**：同一会话第二次提问"那华南呢"，能正确继承上下文；相似历史任务命中时平均步数下降 ≥ 30%。

## FR-05 状态机与决策引擎（P0）
```
INIT → PLAN → RETRIEVE → EXECUTE → CRITIQUE ─┬→ OUTPUT
                          ↑                  ├→ REPLAN（未超预算）
                          └──────────────────┘└→ FAILED（超预算/不可恢复）
```
每个节点落 checkpoint（步号、输入、输出、token 消耗）。决策引擎负责：下一个节点是谁、是否重试、是否降级、是否终止。
**验收**：中途杀掉进程能从未完成的节点续跑，恢复成功率 ≥ 95%。

## FR-06 反思闭环 Critic（P0）
四类失败，四套动作：

| 失败类型 | 检测方式 | 动作 |
|---|---|---|
| SQL 语法/字段错 | 执行异常 | 携带错误信息重写，最多 2 次 |
| 结果为空 | 行数 = 0 | 放宽过滤或换维度，最多 1 次 |
| 数字异常 | 量级/分布校验、与历史值比对 | 交叉校验（换口径重算）再决定是否输出 |
| 幻觉/口径错 | 输出里出现未在 `metric_kb` 命中的口径 | 直接否决，回到 RETRIEVE |

**验收**：50 条评测集上，无反思基线的成功率 vs 有反思的成功率，必须给出对比数字。

## FR-07 多 Agent 协作（P0）
三角色：**Planner**（分解）、**Executor**（调工具）、**Critic**（校验、有否决权）。
**硬约束**：三者只通过结构化产物通信（`TaskDAG` / `ToolCall` / `Verdict`），禁止自由对话。共享记忆走 Redis + Milvus。
**验收**：任何一次执行都能在 trace 里按角色回放。

## FR-08 四种工作流可切换（P1，但强烈建议做）
同一批问题，可切换运行 FC / ReAct / Plan-and-Execute / Multi-Agent 四种模式。
**这是 JD 职责 3 的逐字要求，也是 §8 评测中"横向对比"的唯一素材来源**——面试官问"这四种区别"时，你有数据而不是背定义。

## FR-09 流式交互（P1）
SSE 推送每个节点状态（"正在检索口径…正在执行 SQL…校验通过"）。
**验收**：首字节 < 3s，前端能看到逐步进度。面试 demo 的观感全靠这个。

## FR-10 成本与预算控制（P1）
每次任务设三重预算：最大步数（默认 12）、最大 token、最大时长。超预算按优先级降级：先砍解释性文本 → 再砍多维度下钻 → 最后返回部分结果并标注"未完成"。
**验收**：评测集平均 token 成本可测、可比。

## FR-11 可观测（P1）
Langfuse 接 trace；MySQL 落审计表（任务 ID、每步耗时、token、工具调用、失败原因、最终状态）。
**验收**：任取一次失败执行，5 分钟内能定位到是"规划错/检索错/工具错/模型幻觉"中的哪一类。

## FR-12 安全（P1）
只读 SQL + 表白名单 + 强制 LIMIT；工具参数 schema 校验；**知识库内容一律按数据对待，不按指令执行**（防 prompt injection）；输出脱敏。

## FR-13 评测体系（P1，但决定项目上限）
- 评测集：50 条，分四档（单指标 15 / 对比 15 / 归因 10 / 报表 10），每条带标准 SQL。
- 指标：任务成功率、SQL 首次正确率、平均步数、单任务 token 成本、人工干预率。
- 基线：`纯 LLM 直出 SQL` vs `ReAct` vs `本项目`。
**验收**：出一份一页纸评测报告，四个数字 + 一张对比表。

## FR-14 服务层（P1）
FastAPI 异步：`POST /tasks`（带幂等键）、`GET /tasks/{id}`、`GET /tasks/{id}/stream`、`POST /tasks/{id}/cancel`。Worker 无状态，状态全在 Redis，可水平扩展。
**验收**：50 并发任务不串号、不丢任务；重复提交同一幂等键只执行一次。

# 第六部分：架构

## 6.1 分层

```
接入层    FastAPI（异步 + 幂等 + SSE）
编排层    LangGraph 状态机（PLAN/RETRIEVE/EXECUTE/CRITIQUE/REPLAN）
角色层    Planner / Executor / Critic（同构工具体系，结构化通信）
能力层    工具注册表（schema_search / metric_lookup / sql_execute / python_calc / chart_render）
记忆层    Redis（会话+DAG checkpoint） ｜ Milvus（metric_kb / task_template_kb）
数据层    MySQL（业务数据只读 + 审计日志）
观测层    Langfuse trace + 审计表
部署层    Docker Compose 本地 → K8s（HPA + 队列深度）
```

## 6.2 数据模型（核心三张）

- `task`：id、幂等键、原始问句、解析后任务单、最终状态、总 token、总耗时
- `task_step`：task_id、步号、节点类型、角色、输入快照、输出快照、耗时、token、失败类型
- `audit_log`：工具名、参数、返回值摘要、是否重试、耗时

`task_step` 是全场最重要的表——**它是"可回放"和"可定位失败"的物理载体**，JD 要求 5 直接对应它。

## 6.3 数据集

自建电商数据集 10 张表（用户/商品/订单/订单明细/退款/渠道/地区/活动/库存/成本），约 50 万行，脚本生成，字段语义写进 `metric_kb`。
> 关键决策：**不用公开数据集**。自建才能保证"业务口径"有歧义可讲（退货率是按单还是按件？），而口径歧义正是你做 RAG 和 Critic 的理由。

# 第七部分：技术选型与边界（面试必问"为什么不用 X"）

| 选型 | 分工边界 | 换回触发条件 |
|---|---|---|
| **LangGraph**（编排） | 唯一把状态机当一等公民，checkpoint 天然支持容错续跑 | 若流程退化为纯线性链，可降级为普通链式调用 |
| **LangChain**（组件） | 只做 loader/splitter/retriever/模型适配，不做编排 | 不需要换 |
| **不用 LlamaIndex** | 它的分工是"纯 RAG 索引与检索引擎"；本项目检索要参与决策（要不要重检索、检索什么），交给它等于让出决策权 | 文档量涨到需要多索引结构（层次/图谱/时间感知索引）时，整体替换检索子系统 |
| **不用 CrewAI / AutoGen** | 它们解决"异构角色自由协作"；本项目是同构角色 + 状态机调度，需要细粒度控制与可评测性 | 出现真正异构角色（写码/审码/跑测试）且需要协商时，用 AutoGen 起原型对比 |
| **不用 Swarm** | handoff 与状态机是互斥的控制流模型，只读源码理解机制 | 不引入 |
| **Milvus** | 长期记忆 + 口径检索，JD 加分项直接命中 | 数据量 < 10 万可先用 pgvector，但面试口径按 Milvus 讲 |
| **Redis** | 会话状态 + DAG checkpoint + 队列 | 不需要换 |
| **Python 而非 Java** | JD 硬要求"精通 Python"。你的 Java 底子用在服务层设计（幂等、并发、状态机），不是换语言 | 无 |

# 第八部分：评测方案（决定项目上限的部分）

| 对比组 | 说明 | 预期结论 |
|---|---|---|
| A 基线 | 单次 LLM 直出 SQL | 成功率低、无口径保障 |
| B ReAct | 单 Agent 循环 | 简单问题好，多步易跑偏 |
| C P&E | 先规划后执行 | 步骤确定时 token 最省 |
| D 本项目 | 状态机 + 三角色 + 反思 | 成功率最高，成本居中 |
