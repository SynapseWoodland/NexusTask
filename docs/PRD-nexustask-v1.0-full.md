## 前言

一句话定位：**一个能把失败说清楚的 Text-to-SQL 经营分析 Agent** —— 用户用自然语言问电商交易资金侧的经营数据，系统负责澄清口径歧义、拆解任务、生成只读 SQL、校验结果、必要重算，并把每一次失败归到六类中的一类；全过程可回放、可算成本。

## 三、文档说明

### 3.1 名词解释

| 术语 / 缩略词 | 说明 |
|--------------|------|
| Agent | 由 LLM 驱动、可调用工具、具备多步决策与状态保持能力的执行体。本文特指「规划—执行—校验」三角色协作体 |
| 工作流（Workflow） | Agent 的编排范式。本项目对比四种：Function Calling / ReAct / Plan-and-Execute / Multi-Agent |
| DAG | 有向无环图。Planner 把多步任务拆成带依赖关系的节点图，Executor 按拓扑序执行 |
| 口径 | 同一指标名下的具体计算定义。例：GMV 含税还是不含税、含不含取消单 |
| `metric_kb` | 指标知识库。一个指标对应多条候选口径定义，存于 Milvus，供检索与消歧 |
| `metric_profile` | 基线剖面。按「指标 × 维度 × 月份」记录 P5/P95/均值/标准差，用于判定结果是否离谱（替代「和历史对比」这种不可执行的说法） |
| checkpoint | LangGraph 的状态快照。进程被杀后可从最近快照恢复，是实现「断点续跑」的物理载体 |
| HITL | Human-in-the-loop，人工介入。本项目用 `interrupt_before` 在澄清环节暂停，等用户回复后继续 |
| 五级消歧 | 显式指定 > 会话继承 > 场景默认 > 澄清提问 > 拒答。按序匹配，先命中先返回 |
| contested | 争议题。标准 SQL 本身存疑的评测题，从指标分母剔除并单独报告数量 |
| 六类失败 | `PLAN` / `RETRIEVAL` / `TOOL_ARGS` / `TOOL_EXEC` / `HALLUCINATION` / `BUDGET` |
| 幂等键 | 客户端提交的任务唯一键。同键同参返回首次结果，同键不同参报错 |
| AST 白名单 | 用 sqlglot 把 SQL 解析成语法树，只允许只读节点类型通过；比正则黑名单更难绕过 |
| query rewrite | 追问时把「上一轮问句 + 上下文 + 本轮追问」改写为一条自包含完整问句，再走正常生成链路 |
| 零回归 | 上一基线中通过的题，本次不得变为失败；是合并的一票否决条件 |
| McNemar 检验 | 同一批题上新旧两版结果的配对检验，只统计「通过→失败」(b) 与「失败→通过」(c)，判断差异是否显著 |
| 混合检索 | BM25 稀疏检索 + Dense 向量检索，结果融合后 rerank |
| PARTIAL | 终态之一。未完成全部目标，但已有可交付结果，输出必须标注缺失项与偏差来源 |
| 三重预算 | 步数预算、token 预算、时间预算。任一耗尽即进入降级链 |
| 数值指纹 | 输出中每个数字与工具返回结果做精确比对，用于检测幻觉数值 |
| 数值沙箱 | `sandbox_calc`，受限表达式求值器，只允许引用工具返回值，禁止访问外部资源 |

### 3.2 文档说明

- 本文所有「验收标准」均为可执行判断（是/否），不使用「快速」「稳定」等形容词。
- 「待确认」项**不得成为其闭环时点之后的下游依赖**；不构成下游依赖的待确认项可在开发中并行推进（旧写法「闭环前不得进入下游开发」会与 30 天排期互锁，已废）。
- 本项目的「用户」是岗位需求（JD）与真实使用者的合成；真实用户访谈未开展，见 4.2 声明。

## 四、需求背景

### 4.1 产品 / 数据现状

- **【产品现状】**：目标岗位要求候选人具备「Agent 架构设计 + 评测体系 + 失败归因 + 上下文管理 + 并发与幂等」五项能力。市面同类作品集普遍只演示 happy path，缺少可复算的量化结论，面试中一旦被追问「成功率怎么算的」即失效。
- **【核心问题】**：求职者能在 demo 里跑通一次，但说不出三件事——**成功率的口径、失败的定位、多 Agent 的必要性**。这三件事恰好是面经中被追问最狠的地方。
- **【北极星目标】**：**50 题标准题库的任务成功率**（结果集一致判定）。该指标是项目全部设计的收敛点：消歧、规划、工具、自检、预算，最终都只服务这一个数字。

**业务侧现状（作为数据场景的现实依据）**：

1. 业务方临时取数需排队，平均等 1–2 天（行业常识性描述，本项目不引用具体调研数据）。
2. 同一指标存在多套口径，不同人报出的数不一致，无法直接比较。
3. BI 只能回答已定义好的问题，无法回答「为什么涨了」。

### 4.2 用户调研

| 调研方法 | 样本情况 | 关键结论 |
|---------|---------|---------|
| 目标 JD 拆解 | 1 份（45–75K·16薪，上海） | 硬要求集中在：Agent 框架掌握、评测体系、失败归因、上下文管理、并发与幂等；未出现「对接遗留 Java 系统」要求 |
| 公开面经梳理 | 小红书 / 牛客 2026 年公开帖若干（具体条目与数量待确认，见附录） | 高频追问：为什么需要多 Agent、接口幂等与重复扣费、成功率如何定义、失败如何定位 |
| 同行作品集抽查 | GitHub 同类 NL2SQL / Agent 项目若干（数量待确认） | 普遍缺少标准题库与失败归因，指标口径不可复算 |
| 真实用户访谈 | **未开展** | 本项目为求职作品集，用户价值由 JD 与面经推导，非真实用户验证；不宣称做过用户访谈 |

> 声明：本节不含虚构的访谈样本、用户数量或满意度数据。若后续开展真实访谈，另起版本补充。

### 4.3 竞品分析

| 竞品 | 主要信息 | 关键结论 |
|------|---------|---------|
| QuickBI / FineBI（国内 BI） | 支持自然语言问数，但绑定已建好的指标模型与语义层 | 解决「已定义问题」的取数效率，不解决口径歧义消解；是**替代关系**而非对标对象 |
| SQLChat / Vanna（开源 Text-to-SQL） | 单轮生成 SQL，无状态机、无结果自检 | 只解决「把话翻译成 SQL」，不解决「结果对不对、错了怎么修」 |
| Dataherald（开源 NL2SQL 服务） | 提供训练与评测能力 | 有评测意识，但无失败归因；评测方法可参考，产品形态不可直接复用 |
| 大模型内置数据分析（Code Interpreter 类） | 上传数据即算，无需建模 | 便利但不可审计、口径不可控、结果不可复算 |
| 通用 Agent 框架 demo（LangGraph/CrewAI 示例） | 演示多工具调用与多 Agent 协作 | 普遍无标准题库，无法回答「成功率多少」 |

**结论**：市场空白不在「能不能生成 SQL」，而在「**结果可信度能否被复算、失败能否被定位**」。本项目差异化点即此，且不依赖任何商业产品未公开的能力。

### 4.4 业务场景

**业务一句话**：平台经营分析同学每天要回答「昨天/上周/上月卖了多少、退了多少、为什么」，数据分散在订单、明细、支付、退款、结算五张事实表里；同一个指标有多个口径，取数靠自己写 SQL，跨表下钻一次要半小时。

**业务链路（一笔订单的资金流向）**

```
下单            支付              履约            售后              结算
fact_order  →  fact_payment  →  （不建模）  →  fact_refund  →  fact_settlement
商品/运费/税/优惠   支付渠道/状态                    仅退款/退货退款      扣佣金/净额
```

**三类真实问题（角色 → 问题 → 决策）**

| 角色 | 典型问题 | 用结果做什么决策 | 涉及事实表 |
|---|---|---|---|
| 电商运营 | 上月华东 GMV 多少，环比怎么样？ | 决定区域投放要不要加预算 | `fact_order` + `dim_merchant` |
| 财务 / 资金 | 本月退款率为什么涨了？哪些商家和品类贡献最大？ | 找商家沟通、调整结算节奏 | `fact_refund` + `fact_order` + `fact_settlement` |
| 商家运营 | 客单价掉了 8%，是新客拉低还是老客不买了？ | 决定补贴发给谁 | `fact_order` + `fact_payment` |

**端到端示例（C 档题的完整链路）**

问：「上月退款率为什么涨了？按品类拆一下，找出贡献最大的 3 个。」

1. 消歧：「退款率」按金额还是按单 → 用户答按金额；「上月」= 相对 `as_of_date` 的 2026-06。
2. 规划：DAG = ① 分品类取 2026-05 / 2026-06 的支付金额与退款金额 → ② `sandbox_calc` 算退款率与贡献度 → ③ 取 Top3 品类 → ④ Critic 校验区间与数值指纹。
3. 输出：表格（品类 / 5 月退款率 / 6 月退款率 / 变化 / 贡献度）+ 一句结论 + 所用 `definition_id` 与渲染后的 SQL。

**业务价值 → 技术指标的传导链**

本文有两套问题陈述：4.1 说的是「求职者讲不清」，4.4 说的是「运营取数慢」。二者由下面这条链路连起来，**北极星指标是这条链路的末端测点，不是独立目标**：

| 层 | 内容 |
|---|---|
| 业务侧现状（场景假设，非调研数据） | 运营每周取数若干次，单次排队 1–2 天、自己写 SQL 约 30 分钟；同一指标不同人算出不同数，靠对数解决 |
| 本项目改变的环节 | 等待时间：1–2 天 → 30 秒内出结果；口径一致性：口头约定 → `definition_id` 可溯源；归因：BI 只能给数 → 给出贡献度拆分 |
| 可测量的替代指标 | 单题端到端耗时（人工 30 分钟 vs Agent P95 <20s）、口径可溯源率（输出中 `definition_id` 覆盖率 = 100%）、任务成功率（= 结果集与标准答案一致，代表"它给的数能直接用"） |
| 边界声明 | 数据为合成，**数字代表能力上限而非真实业务收益**；不宣称替代任何 BI 产品，不承诺真实用户量级 |

> 4.2 已如实写明未开展真实用户访谈，因此本节所有业务侧数字标注为「场景假设」。**用可复算的技术指标替代不可获得的用户数据**，是这个项目在无法做用户调研时唯一诚实的论证方式。

### 4.5 数据模型（11 表）

**时间基准**：数据覆盖 2024-07-01 ~ 2026-06-30 共 24 个月；系统固定 `as_of_date = 2026-07-01`，所有「上月 / 本季度 / 近 30 天」相对它计算，**不读系统当前时间**——否则同一道评测题隔天跑出不同答案，成功率不可复现。

| 表 | 类型 | 粒度（一行 = ?） | 主键 | 行数 | 关键字段 | 存在理由 |
|---|---|---|---|---|---|---|
| `dim_merchant` | 维 | 一个商家 | `merchant_id` | 2,000 | `merchant_name`、`merchant_type`（品牌商/经销商/个体）、`settle_cycle`（T+1/T+7）、`commission_rate`、`region`（华东/华南/华北/西南）、`province`、`is_active` | 退款归因主对象；结算周期与佣金率影响资金口径 |
| `dim_product` | 维 | 一个 SKU | `product_id` | 20,000 | `product_name`、`category_id`、`brand`、`list_price`、`tax_rate`（0.06/0.13）、`is_active` | 含税/不含税口径的税率来源 |
| `dim_category` | 维 | 一个类目 | `category_id` | 300 | `category_name`、`parent_id`、`level` | 一/二/三级类目下钻 |
| `dim_channel` | 维 | 一个销售渠道 | `channel_id` | 20 | `channel_name`、`channel_type`（自营/平台/直播/分销） | 渠道对比题 |
| `dim_campaign` | 维 | 一次活动 | `campaign_id` | 200 | `campaign_name`、`campaign_type`（满减/折扣/直播/大促）、`start_date`、`end_date`、`budget` | 归因题最后一层下钻 |
| `dim_date` | 维 | 一天 | `date_id`（YYYYMMDD） | 731 | `date`、`year`、`quarter`、`month`、`week_of_year`、`day_of_week`、`is_workday`、`is_month_end` | **连续时间轴**：趋势/同比题必须能从无数据的期补 0，否则序列缺行、环比错位 |
| `fact_order` | 事实 | 一个订单（头） | `order_id` | 120,000 | `merchant_id`、`customer_id`、`is_first_order`、`channel_id`、`campaign_id`、`order_time`、`order_status`（created/paid/cancelled/refunded/closed）、`goods_amount`、`freight_amount`、`discount_amount`、`tax_amount`、`payable_amount`、`paid_amount` | **口径歧义的物理载体**：状态 / 税 / 运费 / 优惠 |
| `fact_order_item` | 事实 | 订单里的一行商品 | `item_id` | 260,000 | `order_id`、`product_id`、`quantity`、`unit_price`、`item_amount`、`item_discount`、`item_tax`、`refund_qty` | 按商品/类目拆解；订单头粒度做不到 |
| `fact_payment` | 事实 | 一笔支付流水 | `payment_id` | 105,000 | `order_id`、`pay_channel`（支付宝/微信/银联/余额）、`pay_time`、`pay_amount`、`pay_status`（success/failed/closed） | 「支付口径」与「下单口径」的差异来源 |
| `fact_refund` | 事实 | 一笔退款流水 | `refund_id` | 18,000 | `order_id`、`payment_id`、`refund_type`（仅退款/退货退款）、`refund_reason`、`refund_amount`、`refund_status`、`refund_time`、`is_after_sale` | 退款率按单/按金额、售后期口径 |
| `fact_settlement` | 事实 | 一个商家一个月的结算单 | `settlement_id` | 48,000 | `merchant_id`、`settle_month`、`gross_amount`、`refund_amount`、`commission_amount`、`net_amount`、`status`（settled/pending） | 资金侧闭环；净收入口径。**与 `dim_merchant` 的 2,000 商家 × 24 个月对齐**；不含订单/退款外键，不可直接下钻，见下 |

合计约 57 万行。**上一版把 `fact_settlement` 写成「商家一天的结算单 / 30,000 行」，与 2,000 商家 × 24 个月物理上对不上（正确值应为 144 万行），已改为「商家 × 月 / 48,000 行」——粒度与 `settle_cycle` 无关，`settle_cycle` 只描述资金到账时点。**

**关系（ER）**

```
dim_category 1─n dim_product 1─n fact_order_item n─1 fact_order
dim_merchant 1─n fact_order 1─n fact_payment
                           1─n fact_refund
                           1─n fact_order_item
dim_channel  1─n fact_order
dim_campaign 1─n fact_order
dim_merchant 1─n fact_settlement
dim_date     1─n fact_order / fact_payment / fact_refund（按日期列关联）
```

**关于 `customer_id`**：它是脱敏的合成客户编号（`C00001` 形式），**没有 `dim_customer` 维度表**——本项目不建模姓名/性别/年龄等画像属性（无 PII）。「新客 / 老客」判定由 `fact_order.is_first_order`（该客户首单标记）承担，足以支撑 4.4「客单价掉了 8%，是新客拉低还是老客不买了」这类题。

**`dim_date` 为什么必须加回**：时间序列若用事实表 `GROUP BY DATE_FORMAT(...)` 生成，**某期无数据就没有那一行**（如某品类某月零退款）。后果是趋势图断点、环比对上上一期（缺行被当 0 还是跳过，两种都错）。加一张 731 行的日历表，代价可忽略，且 `is_month_end` / `is_workday` 直接支撑「月末 / 工作日」这类问法。

**`fact_settlement` 不可下钻的处理**：该表只有 `merchant_id + settle_month`，没有订单/退款外键，因此**净收入按商家×月口径取 `SUM(net_amount)`**；需要下钻到订单或品类时，走等价推导口径 `SUM(success 支付) − SUM(success 退款) − 佣金`，佣金由 `dim_merchant.commission_rate` 计算。**两条路径必须逐商家逐月对账一致**（见下方「结算不变量」），所以「净收入归因到品类」类题目仍然可做、且可验证。

**三组歧义在数据层的物理锚点**

| 歧义 | 物理锚点 | 两种算法为什么会有差 |
|---|---|---|
| GMV 含税 / 不含税 | `fact_order.tax_amount`、`dim_product.tax_rate` | 13% 与 6% 税率混合，整体差 8–11% |
| GMV 含不含取消单 | `fact_order.order_status` | 取消单占 6–9% |
| GMV 含不含运费 | `fact_order.freight_amount` | 运费占 2–4% |
| 退款率按单 / 按金额 | `COUNT(refund_id)` vs `SUM(refund_amount)` | 小件商品退款单多、金额小，两者可差 1 倍 |
| 退款率含不含售后期 | `fact_refund.is_after_sale` | 售后期后退款占 15–20% |
| 客单价按支付 / 按下单 | `fact_payment.pay_amount` vs `fact_order.payable_amount` | 含部分支付与失败支付，差 3–8% |
| 客单价含不含退款 | `paid_amount − refund_amount` | 高退款品类差 10%+ |

**口径字典（场景默认口径，供五级消歧第 3 级使用）**

| 指标 | 场景默认口径 | 计算方式 | 常见竞争口径 |
|---|---|---|---|
| GMV | 已支付订单的商品金额，不含税、不含运费、剔除取消单 | `SUM(goods_amount - discount_amount)`，`order_status IN ('paid','refunded')` | 含税 / 含运费 / 含取消单 |
| 净收入 | 已结算净额，按结算时点归属 | `SUM(net_amount)`，`fact_settlement.status = 'settled'` | 按支付时点 / 按退款后净额 |
| 退款率 | 退款金额 / 支付金额，含售后期 | `SUM(refund_amount) / SUM(pay_amount)`，两侧均取 `success` | 按单 / 不含售后期 |
| 客单价 | 支付金额 / 支付订单数 | `SUM(pay_amount) / COUNT(DISTINCT order_id)`，取 `pay_status='success'` | 按下单金额 / 扣退款 |

> 每个指标的默认口径必须能在评测中作为「未指定时的预期答案」；用户显式指定竞争口径时，标准答案随之切换——这是消歧正确率可判定的前提。

**每个指标的维度全集（写入 `metric_kb` 的 `dimensions` 字段）**

LLM 不检索表结构、只见声明式指标定义（见 7.1），因此**「用户能按什么维度拆」完全由这张表决定**，必须在这里穷举，否则能力缺口不会暴露、只会静默失效。

| 指标 | 允许维度全集（任意 ≤2 维组合都必须可用） |
|---|---|
| GMV | 时间（日/周/月/季/年）、商家（地区/省/类型/结算周期）、类目（1–3 级）、渠道、活动 |
| 净收入 | 时间（月/季/年）、商家（地区/类型/结算周期）。**不下钻到商品/订单层**（见上「不可下钻的处理」） |
| 退款率 | 时间（日/周/月/季）、商家、类目、渠道、退款类型、是否售后期 |
| 客单价 | 时间、商家、类目、渠道、支付方式、是否新客（`is_first_order`） |

> 结构校验（Planner 输出校验层，不是工具）负责拦截不在全集内的维度，回灌重试最多 3 次，仍非法则拒答并列出该指标支持的维度。

**合成数据规则**

- 固定随机种子；每笔订单满足恒等式 `goods_amount − discount_amount + freight_amount + tax_amount = payable_amount`（四舍五入到分），生成后跑一次全量恒等式校验，不通过即中止。
- 状态分布：paid 88% / cancelled 7% / refunded 5%；跨表外键完整性 100%。
- **退款链路不变量（生成后全量跑，任一条不通过即中止）**：
  1. 同一 `order_id`：`SUM(fact_refund.refund_amount) ≤ fact_order.paid_amount`；
  2. `SUM(fact_refund.refund_amount) ≤ SUM(fact_payment.pay_amount)`（均取 success）；
  3. 每笔 `fact_refund.payment_id` 必须存在于 `fact_payment` 且 `pay_status='success'`；
  4. `is_after_sale=1` 的退款，其 `refund_time − order_time` 必须落在口径字典定义的售后期内（T+15 天）；`is_after_sale=0` 则必须在期外。
- **结算不变量**：对每个 `(merchant_id, settle_month)`：`net_amount = SUM(success pay_amount) − SUM(success refund_amount) − commission_amount`，且 `commission_amount = gross_amount × dim_merchant.commission_rate`（容差 0.01）。
- 24 个月含季节性（618 / 双 11 峰值），并在第 18 个月对一个品类注入一次真实可解释的退款率突增——C 档归因题必须有 ground truth 原因，否则「归因正确」无法判定。
- 商家名、商品名、品牌名全部虚构（如「星野数码」「云栖家电」），不使用真实商标；无姓名 / 手机号 / 地址 / 证件号。

**为什么不直接复用已有仓库 SemanticMindSQL 的数据集**

| 项 | 能否复用 | 结论依据 |
|---|---|---|
| 业务表结构 | 否 | 只有 4 维 1 事实（`dim_region` / `dim_customer` / `dim_product` / `dim_date` / `fact_order`），无退款、结算、支付流水、税、运费、订单状态字段——三组口径歧义在数据层根本不存在 |
| 业务数据 | 否 | 114 行订单、3 个月跨度、`dim_date.quarter` 写死 `Q1`：同比/环比不可做，20 并发与 P95 更无压力可言 |
| 元数据表结构 | 是 | `table_info` / `column_info` / `metric_info` / `column_metric` 的 role（fact/dim、measure/dimension）+ alias + `is_enum` + examples 设计，直接作为 `schema_snapshot` 与 `metric_kb` 的元模型 |
| 命名约定 | 是 | `dim_*` / `fact_*` 前缀与 fact/dim 角色，Planner 输出的结构校验层依赖这套约定（注意：它是进程内的校验函数，**不是工具注册表里的一个工具**） |

> 补充：该仓库的 `dim_customer` 使用中文人名、`dim_product` 使用真实品牌，与本文「全合成、无 PII、无商标」的合规声明冲突，即使扩表也不建议沿用其维度数据。

### 6.3 功能说明

---

#### 6.3.1 FR-01 任务接入与澄清

**需求描述**

接收自然语言问句，完成意图解析与指标识别；命中口径歧义时，按五级消歧（显式指定 > 会话继承 > 场景默认 > 澄清提问 > 拒答）处理，澄清不超过 2 轮。

四类触发器：

| 触发器 | 说明 |
|--------|------|
| 显式提问 | 用户在输入框直接提问 |
| 追问 | 基于上一轮结果继续问（「那华东呢」） |
| 模板复用 | 命中 `task_template_kb` 的历史问题结构，仅替换时间/维度 |
| 定时重跑 | 对已保存问题按周期重跑（仅演示，不接真实调度） |

**追问处理策略（双路径）**

追问（「那华东呢」）走两条路径，由**变更后语义是否唯一确定**决定（不是由「AST 能不能改」决定）：

**快路径准入判据（三条同时满足才准入）**

只有同时满足下面三条，才允许不走 LLM：

1. **粒度不变**：上一轮 SQL 的 GROUP BY 列集合不变；
2. **被测对象不变**：所用 `definition_id` 的 measure / filters 表达式不变；
3. **值域可解析**：追问里新出现的维度值能唯一映射到物理列值（枚举表 / 别名表命中），不需要语义判断。

| 常见形态 | 例子 | 粒度 | measure | 值域 | 快路径 |
|---|---|---|---|---|---|
| 字面量替换（原本已有该条件，只换值） | 「上月是 6 月，那换成 5 月呢」 | 不变 | 不变 | 可解析 | ✅ |
| 排序 / 截断 | 「只看前 10」 | 不变 | 不变 | — | ✅ |
| 追加过滤（原本没有该条件） | 「那华东呢」「只看退款成功的」 | 不变 | 不变 | 可解析 | ✅ |
| 聚合函数变化 | 「改成平均」 | 不变 | **变**（本质是换 definition） | — | ❌ 主路径 |
| GROUP BY 变化 | 「按渠道拆」 | **变** | 不变 | 类目层级常带歧义（一级/二级） | ❌ 主路径 |
| 撤销 GROUP BY | 「给我看明细」 | **变**（→ 行级） | 不变 | — | ❌ 主路径 |
| 换口径 / 换指标 | 「那按金额算呢」 | — | **变** | — | ❌ 主路径 |

> **为什么不是「凡能改 AST 的都走快路径」**：「GROUP BY 变化」在单指标、层级已定稿时也能机械改写，但类目层级歧义是常态，走规则会绕开澄清；且它改的是 grain，一旦标准答案按另一层级定义，错得还很像对的。**能改 ≠ 该改**，判据是「语义唯一确定」，不是「AST 可编辑」。
> 「GROUP BY 变化」是快路径实验证明收益显著后的**第一个扩展项**，不进 P2 首版。

| 路径 | 触发条件 | 做法 | 优先级 |
|---|---|---|---|
| 主路径：query rewrite + 重新生成 | 默认路径，覆盖全部追问 | 将「上一轮问句 + 已确认口径 + 上一轮 SQL 结构 + 本轮追问」改写为一条**自包含**完整问句，再走 FR-02 正常规划链路 | P0 |
| 快路径：AST 差分 | 同时满足上述三条判据 | sqlglot 解析上一轮 SQL → 规则引擎识别变更 → 直接改写 AST 并重新渲染，不调用 LLM | P2（实验，先量化收益再决定是否保留） |

规则：

- 三条判据任一不满足 → 主路径。**「换口径 / 换指标」天然不满足第 2 条**；唯一例外是新旧 `definition_id` 的 measure 与 filters 完全相同、仅 dimensions 不同，此时退化为「追加过滤」判定。
- AST 解析失败、schema 校验不通过、或 Critic 四项检查不通过 → **降级到主路径**，不做二次猜测。
- 规则引擎的分类结果必须落库（`followup_route` 埋点），用于事后统计误分类率；误分类导致降级的样本进入回归题库。
- 快路径不引入第二套 SQL 生成逻辑：两条路径共用同一渲染器、白名单、AST 校验与审计。
- 快路径的收益必须用数据说话：在追问子集上对比「主路径成功率 / 延迟 / 成本」与「快路径成功率 / 延迟 / 成本」，无显著收益则删除。
- 口径切换与维度切换叠加（「那按金额算的华东呢」）= G + D，必须走主路径一趟改写，不得拆成两次追问。

**交互流程**

1. 提交问句 → 生成/校验幂等键 → 命中已完成任务则直接返回首次结果。
2. 若判定为追问 → 按双路径处理，产出自包含问句（快路径直接出结果则跳至第 7 步）。
3. **指标识别（复数）** → 问句中的所有指标与维度分别检索 `metric_kb` → 各自返回候选集（0 / 1 / N 条）。
4. 全部指标唯一命中且高置信 → 直接进入 PLANNING。
5. 部分多候选 → 逐项检查「显式指定」「会话继承」，命中即定稿。
6. 仍有未定稿项 → 进入 CLARIFYING，`interrupt_before` 暂停，前端**同时**渲染所有未定稿指标的候选卡。
7. 用户提交 → 恢复执行；**一次提交可同时定稿多个指标**；未选且用尽澄清批次 → 未定稿项取场景默认口径并在结果中逐项标注。
8. 口径不可消解（如问句本身矛盾）→ 拒答并说明原因。

**页面元素**

| 元素 | 类型 | 说明 | 校验规则 |
|------|------|------|---------|
| 问句输入框 | 多行文本 | 上限 500 字 | 非空；长度 ≤ 500；去除首尾空白后非空 |
| 发送按钮 | 按钮 | 提交任务 | 输入框为空时置灰 |
| 示例问句 | 快捷标签 ×4 | 覆盖 A/B/C/D 四档题型各一条 | — |
| 口径候选卡 | **多组单选卡片**（一个未定稿指标一组） | 展示候选定义、差异说明、默认标记；维度歧义（如类目层级）用下拉选择 | 每个未定稿指标各选 1 项才可提交；一组都未选时确认按钮置灰 |
| 确认按钮 | 按钮 | 提交选择 | 未选择时置灰 |
| 都不对 | 文本按钮 | 首次点击 → 放宽相似度阈值重新检索、渲染第二批候选（二次澄清）；再次点击 → CLARIFYING → FAILED（`failure_class=RETRIEVAL`），该终态下可转工单 | 每任务最多 1 次；转工单只在 FAILED/PARTIAL 终态可用 |

**异常处理**

| 异常场景 | 处理方式 |
|---------|---------|
| 网络异常（提交失败） | 前端保留输入，提示「提交失败，请重试」，不消耗澄清批次 |
| 服务端 5xx | 返回可读错误码；任务不落库，幂等键可重试 |
| 输入异常（超长/空/纯符号） | 前端拦截并提示具体原因，不发请求 |
| 意图无法映射到任何指标 | 拒答，列出当前支持的指标清单 |
| 追问时上一轮上下文缺失（会话过期/内存降级） | 提示「上一轮信息不可用」并要求补全问句，不猜测上一轮口径 |
| 澄清批次超限 | 未定稿项取默认口径继续，结果区顶部标注「口径为系统默认，可能与你的预期不同」 |
| 权限异常 | 本项目为单机演示，无多租户；预留 `X-Tenant-Scope` 透传但不启用鉴权（待确认是否演示） |

**埋点需求**

- `task_submit`：问句长度、是否命中模板、幂等键是否重复。
- `clarification_shown`：候选数量、触发层级（多候选 / 低相似度 / 不可消解）。
- `clarification_answered`：所选定义 ID、是否首轮解决、耗时。
- `followup_route`：路径（rewrite / ast_diff）、变更形态（A–G）、三条判据中哪条不满足、是否降级及降级原因。

**验收标准**

- [ ] 50 题中所有需要消歧的题目，均能返回 ≥2 条候选定义，无一条静默取默认且不标注。
- [ ] **澄清批次上限 2 次交互**（一次交互内可同时定稿多个指标）：构造需要第 3 次交互才能定完的用例，系统必须对未定稿项取默认口径并在输出中逐项标注。
- [ ] ≥4 条多指标题（C 档，含「退款率 + 品类层级」这类双歧义）能在**单次澄清交互内**完成全部指标定稿。
- [ ] 同一幂等键重复提交 5 次，返回结果完全一致且数据库仅 1 条任务记录。
- [ ] 输入框输入 501 字时前端拦截，不发起网络请求。
- [ ] 追问子集（≥8 题）在主路径下全部被改写为自包含问句：送入 Planner 的 Prompt 中不出现「上一轮原话直接拼接」的形态。
- [ ] 若启用快路径：满足三条判据的追问（字面量替换 / 排序截断 / 追加过滤 各 ≥3 题）改写结果与主路径一致率 ≥95%，不一致样本必须能归因到具体规则；不满足判据的形态（聚合函数变化、GROUP BY 变化、撤销 GROUP BY、换口径 / 换指标）100% 降级到主路径，规则引擎误判样本进回归题库。
- [ ] 口径切换类追问（≥4 题）必须正确定稿 `definition_id`，最终 SQL 的 measure / filters 与所选口径定义逐字段一致；口径切换 + 维度切换叠加的追问（≥2 题）必须在一次改写内完成。

#### 6.3.2 FR-02 Planner DAG

**需求描述**

将多步问题拆成带依赖的 DAG，输出严格符合 JSON Schema；结构校验失败时在重试预算内重新生成，禁止「让 LLM 自己执行到哪算哪」。

**交互流程**

1. 接收已定稿口径 + 问句 + 可用工具清单（含参数 schema）。
2. LLM 输出 DAG JSON。
3. 结构校验：JSON 可解析 → 必填字段齐全 → 工具名在注册表 → 参数符合 schema → 无环 → 节点数 ≤ 8。
4. 校验通过 → 进入 EXECUTING；失败 → 将校验错误回灌给模型重新生成（重试预算默认 2 次）。
5. 预算耗尽 → FAILED，失败类 `PLAN`。

**页面元素**

| 元素 | 类型 | 说明 | 校验规则 |
|------|------|------|---------|
| DAG 缩略图 | 只读图形 | 进度区展示节点与依赖 | 仅在「调试模式」下展开完整 JSON |
| 节点卡片 | 只读卡片 | 工具名 + 参数摘要 + 状态 | 参数中含口径 `definition_id` 时高亮 |

**异常处理**

| 异常场景 | 处理方式 |
|---------|---------|
| 输出非 JSON | 提取首个 `{...}` 块重试；失败计入 `PLAN` |
| 工具名不在注册表 | 回灌合法工具名清单重试 |
| 参数缺失/类型错误 | 回灌 JSON Schema 重试 |
| DAG 成环 | 拒绝执行，直接重规划 |
| 节点数 > 8 | 拒绝执行，提示「问题过于复杂，请拆分」，计入 `PLAN` |

**埋点需求**

- `plan_generated`：节点数、工具种类、生成耗时、token 消耗。
- `plan_validation_failed`：失败原因枚举、重试序号。

**验收标准**

- [ ] 构造 10 条非法 DAG（非 JSON / 成环 / 未知工具 / 缺参 / 超节点数等），系统 100% 拦截，无一条进入执行。
- [ ] 重试预算耗尽后任务终态为 FAILED 且 `failure_class = PLAN`，在看板中可见。
- [ ] 合法 DAG 的执行顺序严格符合拓扑序：构造 n2 依赖 n1 的用例，日志中 n1 完成时间早于 n2 开始时间。

#### 6.3.3 FR-03 工具集成层

**需求描述**

统一工具注册表，7 个工具（4 只读 SQL + `sandbox_calc` + `chart_render` + `create_ticket`），全部通过注册表暴露 schema；SQL 类工具强制只读、表/列白名单、AST 节点校验、强制 LIMIT、超时熔断。

| 工具 | 类型 | 用途 | 关键约束 |
|------|------|------|---------|
| `sql_query_metric` | 只读 | 单指标聚合 | 必带 `definition_id`；LIMIT 1000；超时 10s |
| `sql_query_dimension` | 只读 | 按维度下钻 | 维度必须在白名单；LIMIT 1000 |
| `sql_query_trend` | 只读 | 时间序列 | 时间粒度 ∈ {day, week, month}；跨度 ≤ 24 个月 |
| `sql_query_contribution` | 只读 | 贡献度/归因拆解 | 分组数 ≤ 50 |
| `sandbox_calc` | 纯计算 | 比率、环比、占比、贡献度 | 只能用工具返回的变量；禁用 `import`/文件/网络 |
| `chart_render` | 渲染 | 生成图表配置 | 仅接受已存在的结果集引用 |
| `create_ticket` | 幂等写 | 创建分析工单 | 必带幂等键；同键同参返回首次结果 |

**交互流程**

1. Executor 按 DAG 拓扑序取节点 → 校验参数 → 注入 `definition_id` 与日期范围。
2. SQL 由渲染器按「声明式指标定义 + 结构化参数」生成，**不接受 LLM 直接拼接的 SQL 字符串**；渲染后先过 AST 节点白名单（FR-12）再执行。
3. 执行 → 捕获异常/超时 → 返回结构化结果或结构化错误（不抛裸异常）。
4. 结果写入任务态，供下游节点与 Critic 使用。

**页面元素**

无独立页面。进度区以工具卡片呈现：工具名、参数摘要、耗时、返回行数、状态徽标。

**异常处理**

| 异常场景 | 处理方式 |
|---------|---------|
| SQL 超时（>10s） | 中断查询，返回 `TOOL_TIMEOUT`，计入 `TOOL_EXEC` |
| SQL 语法/执行错误 | 返回错误码 + 脱敏后的错误摘要（不含表名以外信息），交由 Critic 判定是否重写 |
| 返回 0 行 | 不视为错误，交由 Critic 判定是否为空数据场景（D 档题型） |
| 返回行数超上限 | 截断并标记 `truncated=true`，结果区提示 |
| 参数含未知表/列 | 请求前拦截，返回 `SCHEMA_MISMATCH`，不回灌给模型猜测 |
| 注入尝试（问句含 `; DROP` 等） | 在参数层被模板化吸收，不进入 SQL 文本 |

**埋点需求**

- `tool_call_start` / `tool_call_end`：工具名、耗时、返回行数、状态、是否截断。
- `sql_validation_failed`：拦截原因（表白名单/列不存在/非只读/超 LIMIT）。

**验收标准**

- [ ] 构造 10 条注入型问句（含 `; DROP TABLE`、`UNION SELECT`、注释截断等），0 条产生写操作，0 条返回非白名单表数据。
- [ ] 单次 SQL 查询耗时上限 10s：构造慢查询，系统在 10s 内中断并返回 `TOOL_TIMEOUT`。
- [ ] 结果行数上限 1000：构造返回 5000 行的查询，实际返回 ≤1000 且 `truncated=true`。
- [ ] `create_ticket` 同键重复调用 10 次，工单表仅 1 条记录。

#### 6.3.4 FR-04 长短期记忆

**需求描述**

短期记忆存会话上下文与状态快照（Redis）；长期记忆存指标知识库与任务模板库（Milvus）。`metric_kb` 中每个指标存 ≥2 条候选口径，是歧义能被消解的物理前提。

**交互流程**

1. 会话开始 → 创建 session，写入 Redis。
2. 每轮问句 → 合并「当前轮 + 压缩后的历史摘要 + 已确认口径」。
3. 指标检索 → `metric_kb` 返回候选集（含相似度分数）。
4. 任务结束 → 若问题结构可复用，写入 `task_template_kb`。
5. 会话超过 N 轮 → 历史按模板压缩为结构化摘要（保留指标、口径、时间范围、维度），不保留自然语言原文。

**页面元素**

| 元素 | 类型 | 说明 |
|------|------|------|
| 会话列表 | 侧边栏（调试模式） | 会话 ID、首问摘要、状态 |
| 已确认口径标签 | 只读标签 | 展示当前会话继承的口径，可点击查看定义 |

**异常处理**

| 异常场景 | 处理方式 |
|---------|---------|
| Redis 不可用 | 降级为无状态单轮模式，提示「多轮上下文不可用」，不阻断单轮任务 |
| Milvus 不可用 | 降级为 BM25 单路检索；若仍无结果，进入澄清或拒答 |
| 检索返回 0 条 | 不臆造指标定义，直接拒答并列出支持指标 |
| 相似度并列（差值 < 0.02） | 视为多候选，强制走澄清 |

**埋点需求**

- `memory_retrieve`：指标 key、候选数、Top1 相似度、是否降级。
- `template_reused`：模板 ID、替换的槽位。

**验收标准**

- [ ] `metric_kb` 中 GMV / 退款率 / 客单价 各含 ≥2 条候选定义，字段完整（定义、声明式字段 measure/agg/filters/dimensions/time_field、参数化渲染模板、口径说明），且模板不含可被外部输入拼接的原始字符串。
- [ ] **D9 之前（只有单路 Dense）**：拔掉 Milvus → 降级 BM25 单路，A 档成功率 ≥ 单路 Dense 的 90%。
- [ ] **D9 之后（混合检索 + rerank）**：混合检索相比单路 Dense 的 A 档成功率 ≥95%（不下降）；「Milvus 不可用 → 降级 BM25」与「混合检索」是两条不同路径，分开验收。
- [ ] FR-04b（P1）：Top-1 命中率 ≥ 单路 Dense + 5pp。
- [ ] 会话摘要 ≤1.5k token；第 6 轮上下文不超过第 1 轮的 1.2 倍；第 20 轮摘要仍 ≤1.5k token。
- [ ] 检索 Top1 与 Top2 相似度差 < 0.02 时，系统必进澄清，不得直接取 Top1。

#### 6.3.5 FR-04b RAG 优化（P1）

**需求描述**

在基础单路向量检索之上，引入 BM25 + Dense 混合检索与 rerank，用同一套检索评测集对比命中率。

**交互流程**

1. 问句同时进入 BM25 与 Dense 两路。
2. 分数归一化后加权融合（权重待 D9 调参确定）。
3. Top-20 进入 rerank 模型，取 Top-5 注入 Prompt。
4. 记录两种检索方式的 Top-1/Top-3 命中情况。

**页面元素**

无独立页面。调试模式下展示候选列表与各分数。

**异常处理**

| 异常场景 | 处理方式 |
|---------|---------|
| rerank 模型不可用 | 跳过 rerank，直接用融合分；记录降级标记 |
| 两路均低分 | 进入澄清或拒答，不得低分强取 |

**埋点需求**

- `retrieval_compare`：问题 ID、BM25 Top1、Dense Top1、Fusion Top1、Rerank Top1、是否命中。

**验收标准**

- [ ] 在 ≥30 条检索评测问题（从 50 题中取）上，混合检索 + rerank 的 Top-1 命中率高于单路 Dense 至少 5 个百分点。
- [ ] rerank 不可用时自动降级且不报错，任务仍可完成。

#### 6.3.6 FR-05 状态机与恢复

**需求描述**

LangGraph 10 态状态机，**节点级 checkpoint**；支持进程级恢复、任务取消、幂等去重。

**交互流程**

1. 每个 DAG 节点执行**前**写节点级 checkpoint（含任务态、已完成节点集合、当前节点、预算余量、节点输出引用）；执行后再写一次完成标记。
2. 状态迁移只写状态日志，不单独持久化快照——状态可由最近一次节点 checkpoint 推导。
3. 进程重启 → 扫描未终态任务 → 从最近 checkpoint 恢复，已完成节点直接读回输出引用，不重放 LLM 与工具调用。
4. 用户点「取消」→ 置取消标记 → 在当前节点结束后进入 CANCELLED，不回滚已完成的结果。
5. 幂等键重复提交 → RECEIVED 阶段直接短路返回。

**页面元素**

| 元素 | 类型 | 说明 |
|------|------|------|
| 取消按钮 | 按钮 | 执行中可见；置灰条件为已进入终态 |
| 状态徽标 | 只读标签 | 展示当前 10 态之一 |
| 恢复提示条 | 提示条 | 检测到进程重启恢复时显示 |

**异常处理**

| 异常场景 | 处理方式 |
|---------|---------|
| checkpoint 写入失败 | 任务可继续，但标记 `no_checkpoint`；重启后该任务置 FAILED 并提示重试 |
| 恢复时状态不一致 | 以 checkpoint 为准，丢弃内存态，记录异常日志 |
| 取消时正在执行长 SQL | 不中断当前查询（避免连接泄漏），节点结束后停止后续节点 |
| 同一任务并发提交 | 幂等键 + 处理中状态互斥，第二次请求返回「处理中」 |

**埋点需求**

- `state_transition`：源状态、目标状态、触发条件、耗时。
- `task_resume`：恢复位置、跳过的节点数。
- `task_cancelled`：取消时所在状态、已完成节点数。

**验收标准**

- [ ] 在执行第 3 个节点时 kill -9 进程，重启后任务从第 4 个节点继续，前 3 个节点不重复调用工具（日志计数可验证）。
- [ ] 取消操作从点击到状态变为 CANCELLED 不超过「当前节点剩余执行时间 + 1s」。
- [ ] 20 个请求并发提交同一幂等键，仅 1 个进入执行，其余 19 个返回相同结果或「处理中」。

#### 6.3.7 FR-06 Critic 自检

**需求描述**

对执行结果做四类校验，判定 PASS / REPAIR / REJECT：
1. **结构**：结果集列名/类型是否符合 `expected_output`。
2. **口径**：SQL 实际使用的口径是否与定稿 `definition_id` 一致。
3. **数值**：结果是否落在 `metric_profile` 的合理区间（P5–P95 外触发重算）。
4. **溯源**：输出中每个数字必须能在工具返回中找到。

冷启动（该指标 × 维度 × 月份无基线）→ 跳过数值校验并标注 `no_baseline`，不得伪造基线。

**交互流程**

1. 收集全部工具返回 + DAG + 定稿口径。
2. 逐项校验 → 生成结构化判定。
3. PASS → COMPLETED；REPAIR → REPLANNING（限 1 次）；REJECT → PARTIAL 或 FAILED。

**页面元素**

| 元素 | 类型 | 说明 |
|------|------|------|
| 校验清单 | 只读列表 | 四项校验各自的结果与证据 |
| 基线偏离提示 | 警示条 | 数值越界时显示「结果偏离历史区间，已重算 1 次」 |

**异常处理**

| 异常场景 | 处理方式 |
|---------|---------|
| 无基线（冷启动） | 跳过数值校验，不判失败，输出标注 |
| 重算后仍越界 | 停止重算，按 PARTIAL 输出并标注「结果偏离基线，原因未定」 |
| 溯源失败（数字找不到） | 判 HALLUCINATION，REJECT，不回灌重试（重试会再次编造） |
| Critic 自身输出格式错误 | 按 REJECT 处理并计入 `HALLUCINATION`，不得放行 |

**埋点需求**

- `verify_result`：四项校验各自通过/失败、判定结论、耗时。
- `recompute_triggered`：触发原因（越界/结构/口径）、重算序号。

**验收标准**

- [ ] 构造「SQL 写错（漏了 WHERE 时间条件）」用例，Critic 必须判 REPAIR，重写后结果与标准答案一致。
- [ ] 构造「LLM 输出了一个工具从未返回的数字」用例，Critic 必须判 HALLUCINATION 且不进入重试。
- [ ] 冷启动场景（新指标 × 新维度）不报错、不阻塞，输出含 `no_baseline` 标记。
- [ ] 单任务重算次数硬上限 1 次：构造持续越界用例，验证只触发 1 次重算即转 PARTIAL。

#### 6.3.8 FR-07 三角色结构化协作

**需求描述**

Planner / Executor / Critic 三角色之间**只传结构化产物**（JSON schema 约束），禁止自由对话传递。目的：每层可单测、可回放；避免 Critic 的判定被执行上下文污染。

**交互流程**

1. Planner 产出 DAG JSON。
2. Executor 逐节点执行，产出结果对象数组。
3. Critic 读取 DAG + 结果 + 口径，产出判定 JSON。
4. 判定为 REPAIR 时，把「修复目标节点 + 动作 + 理由」结构化写入 `repair_action`，由状态机据此决定：**目标节点合法 → REPLANNING 后回 EXECUTING 只重跑该节点及其下游；不合法 → 回 PLANNING 全量重规划**。不回传自然语言讨论。

**页面元素**

无独立页面。调试模式可展开三个角色的原始 JSON 产物。

**异常处理**

| 异常场景 | 处理方式 |
|---------|---------|
| 任一角色输出不合 schema | 该角色重试 1 次；仍失败则任务 FAILED 并标注角色名 |
| 角色间字段契约不一致 | 启动时跑契约测试，CI 拦截，不在运行时兜底 |

**埋点需求**

- `role_artifact`：角色名、schema 版本、字段数、耗时。

**验收标准**

- [ ] 代码层面断言：角色间传参只接受 schema 校验通过的对象，自由文本字段为 0 个。
- [ ] 三个角色各自有独立单测：schema 校验分支 + 结构化产物序列化/反序列化 + 契约一致性覆盖；整体行覆盖率 ≥70%，且「FR-07 验收第 1 条（自由文本字段为 0）」相关分支覆盖率 **100%**。
- [ ] 任取一条 trace，可仅凭结构化产物复现该次判定（不依赖对话记录）。

#### 6.3.9 FR-08 工作流对比 + 确定性基线（P1，不可砍）

**需求描述**

同一 50 题、同一工具层、同一模型配置下，对比 Function Calling / ReAct / Plan-and-Execute / Multi-Agent 四种编排范式。

另加一列**确定性基线**：对追问子集中满足快路径三条判据的题，用规则 + AST 改写直接出结果，不调用 LLM，回答「这类题上 LLM 编排到底买到了什么」。

**交互流程**

1. 统一入口 `run(question, mode)`。
2. 四种模式共用工具注册表与安全层。
3. harness 批量跑 → 输出四列对比表（成功率 / 平均步数 / 单任务成本 / P95 延迟 / 失败分布）。
4. 追问子集另跑一次确定性基线（同题、同标准答案），单独成列；该列分母只有子集题量，不与四模式合并排名。

**页面元素**

调试页「模式对比」标签页：四列对比表 + 确定性基线列（灰底、标注子集 n）+ 失败分布堆叠图。

**异常处理**

| 异常场景 | 处理方式 |
|---------|---------|
| 某模式超时率过高 | 单独标注超时率与超时任务占比，**成功率照常计入（超时计失败）**；不得剔除该模式或该题。单模式超时率 >10% 时标注「不稳定」，但仍参与排名 |
| 某模式无法完成某类题 | 记为失败，不剔除题目（保证分母一致） |
| 确定性基线无法处理某追问 | 记为失败并归因（如形态为 E/F，不满足判据），不允许人工补答案 |

**埋点需求**

- `mode_run`：模式名、题目 ID、成功与否、步数、成本、耗时、失败类。
- `baseline_run`：题目 ID、变更类、是否命中确定性规则、耗时。

**验收标准**

- [ ] 50 题 × 4 模式 = 200 次运行全部有记录，无缺失。
- [ ] 四种模式的成功率分母完全相同（同一题库、同一 contested 剔除规则）。
- [ ] 确定性基线的分母单独标注为追问子集（≥8 题），不与四模式并列排名。
- [ ] 能给出「同一道题在四种模式下分别怎么失败」的具体案例 ≥3 个。
- [ ] 能给出「同一道追问在基线与最优模式下的差异」配对案例 ≥3 个（延迟 / 成本 / 正确性）。

**页面元素**

#### 6.3.11 FR-10 预算与降级

**需求描述**

三重预算（步数 / token / 时间），任一超限进入降级链；降级不静默，必须体现在输出中。

**降级链**

```
主模型（全功能）
  → 收窄任务范围（LIMIT 1000→100、时间粒度 month→quarter、砍非关键维度）  ← 先省调用，再省钱
  → 关闭 rerank（省 token；仅在 D9 FR-04b 启用后才有效）
  → 切备用模型（同 schema 能力；须先通过同一套 schema 契约测试）
  → 缩减输出（只给表，不给图）
  → PARTIAL（给出已完成部分 + 缺失项 + 失败类 BUDGET）
```

> 顺序理由：**少一次 LLM 调用比关 rerank 省得多**——收窄范围会直接让下游节点消失，而关 rerank 只省检索侧 token。切备用模型放在其后，因为换模型会带来 schema 遵从率的不确定性，代价高于前两档。

**交互流程**

1. 每节点执行前后扣减预算。
2. 超阈值（如 token 达 80%）→ 打预警标记。
3. 超上限 → 停止新节点 → 走降级链 → 能交付则 PARTIAL，不能则 FAILED。

**页面元素**

| 元素 | 类型 | 说明 |
|------|------|------|
| 预算条 | 进度条 ×3 | 步数 / token / 时间，超限变红 |
| 降级标记 | 徽标 | 显示本任务触发了哪一级降级 |

**异常处理**

| 异常场景 | 处理方式 |
|---------|---------|
| 主模型连续超时 | 自动切备用模型，记录切换点 |
| 备用模型也不可用 | 直接 PARTIAL/FAILED，不回退到「无限重试」 |
| 预算计算偏差 | 以服务端统计为准，前端只做展示 |

**埋点需求**

- `budget_warning` / `budget_exceeded`：维度、已用/上限、触发层级。
- `degrade_applied`：降级级别、触发原因。

**验收标准**

- [ ] 单任务 token 上限可配置，超限后不再发起新 LLM 调用（调用日志可验证）。
- [ ] 触发降级时，输出中必须出现降级标记；删除该标记的构建视为不通过。
- [ ] 单任务成本 P95 按模式分别统计且达标（FC/ReAct ≤ ¥0.25，P&E ≤ ¥0.35，MA ≤ ¥0.6），不采用四模式混合 P95。

#### 6.3.12 FR-11 六类失败自动归因 + 看板（头牌，不可砍）

**需求描述**

每次失败自动归入六类之一，附判定信号；看板按类聚合，支持下钻到 trace。

| 失败类 | 判定信号（自动） |
|--------|-----------------|
| `PLAN` | DAG 结构校验失败且重试耗尽；或节点数超限 |

| `HALLUCINATION` | 数值指纹未命中；或 Critic 自身输出不合 schema |
| `BUDGET` | 步数/token/时间任一超限且未能完整交付 |

**交互流程**

1. 任务终态为非 COMPLETED 时，归因器读取状态轨迹 + 错误记录 + 校验结论。
2. 按优先级匹配判定信号（工具类 > 校验类 > 预算类 > 规划类）。
3. 写入 `failure_attribution` 表，附 trace 链接。

**页面元素**

| 元素 | 类型 | 说明 |
|------|------|------|
| 分布堆叠图 | 图表 | X = 题型档（A/B/C/D）或模式，Y = 数量，色 = 六类 |
| 明细表 | 表格 | 任务 ID、题目、失败类、判定信号、trace 链接 |
| 单类下钻 | 筛选 | 点击某一类过滤明细 |

**异常处理**

| 异常场景 | 处理方式 |
|---------|---------|
| 多条信号同时命中 | 按固定优先级取一条，其余记入 `secondary_signals` |
| 无任何信号命中 | 归入 `UNKNOWN` 并告警；UNKNOWN 占比 >5% 视为归因器缺陷，需修 |
| 归因器自身异常 | 任务仍可结束，归因失败不影响主流程 |

**埋点需求**

- `failure_attributed`：failure_class、signals[]、任务 ID。
- `dashboard_view`：筛选条件、停留时长。

**验收标准**

- [ ] 构造六类失败各 3 个用例（共 18 个），自动归因准确率 100%（人工可复核）。
- [ ] 任取一条失败任务，从看板点击可在 2 次跳转内到达 Langfuse trace。
- [ ] UNKNOWN 占比在 50 题全量跑分中 ≤5%。

#### 6.3.13 FR-12 安全

**需求描述**

五层安全：数据只读、SQL 生成受控、AST 校验、注入防护、脱敏与审计。

| 层 | 措施 |
|----|------|
| 连接层 | 独立只读账号：仅有 10 张分析表的 `SELECT`；无 DDL/DML/FILE 权限；工单表由另一个账号读写；启动时 fail-fast 校验 |
| 生成层 | LLM 不产出 SQL 文本，只产出结构化参数；渲染器按声明式指标定义编译 SQL |
| 校验层 | **sqlglot 解析全树 + 节点白名单**：仅放行 `Select` / `Union` / CTE / `Join` / `Where` / `Group` / `Having` / `Order` / `Limit` 等只读节点；出现 `Insert` / `Update` / `Delete` / `Merge` / `Drop` / `Alter` / `Create` / `Command` / `Transaction` / `Into`（`INTO OUTFILE`）/ `LoadData` 任一节点即拒绝；多语句直接拒绝 |
| 执行层 | 表白名单、列白名单、强制 LIMIT 1000、statement timeout 10s |
| 输出层 | 结果脱敏（本项目无 PII）；审计日志记录「谁在何时以什么口径查了什么」 |

> 正则只保留为「明显恶意输入的即时提示」，**不作为安全边界**。安全边界是 AST 节点白名单 + 数据库最小权限账号两层，二者任一失效另一层仍可阻断。

> 为什么自己渲染的 SQL 还要做 AST 校验：参数值、维度名、时间表达式最终都要拼进 SQL 文本，渲染器的模板缺陷同样会造出危险语句；校验的是**最终字符串**，不是信任渲染器。

**交互流程**

1. 启动时校验 DB 账号权限，若检测到写权限则拒绝启动（fail-fast）。
2. 渲染 → sqlglot 解析 → 遍历全树做节点白名单判定 → 表/列白名单比对。
3. 任一层不通过 → 拒绝执行，返回结构化错误，不把错误内容回灌给模型用于「猜一个能过的写法」。
4. 每次工具调用写审计记录（形状，不含结果内容）。

**页面元素**

无独立页面。调试模式提供「审计日志」标签页。

**异常处理**

| 异常场景 | 处理方式 |
|---------|---------|
| 检测到写权限 | 启动失败并打印修复指引 |
| 命中非白名单节点（含 `INTO OUTFILE`、`LOAD_FILE`、`Command`） | 解析后拦截，返回 `SQL_AST_REJECTED`，请求不发送到数据库 |
| 多语句（分号拼接） | 拦截，返回 `SQL_MULTI_STATEMENT` |
| SQL 解析失败 | 拦截（渲染产物必须可解析），返回 `SQL_PARSE_ERROR`，不回灌重试 |
| 命中非白名单表/列 | 请求前拦截，返回 `SCHEMA_MISMATCH` |
| 审计写入失败 | 查询仍执行，但记录 ERROR 级别日志并告警 |

**埋点需求**

- `security_block`：拦截层级（连接/生成/AST/表白名单/列白名单）、原因。
- `audit_write_failed`：失败原因。

**验收标准**

- [ ] 构造 20 条绕过型 payload（注释截断、`;` 多语句、大小写/空白混淆、`UNION SELECT`、`INTO OUTFILE`、`LOAD_FILE`、Unicode 同形字符），AST 层全部拦截，0 条到达数据库。
- [ ] 直接用只读账号执行 `INSERT` / `UPDATE` / `DELETE` / `DROP`，数据库层全部返回权限错误（证明第二层独立有效，不依赖应用层）。
- [ ] 50 题全量跑分中，`security_block` 事件数为 0（正常题目不应被误拦）。
- [ ] 每次工具调用均有一条审计记录，抽查 20 条，缺失数 0。

#### 6.3.14 FR-13 评测体系（P0）

**需求描述**

50 题标准题库 + 六项指标定义 + 自动比对器 + 跑分 harness + 合并门禁。这是北极星指标的度量工具，先于功能调优存在；没有门禁的跑分只是看板。

**题库分档**

| 档 | 题量 | 内容 | 主要考察 |
|---|---|---|---|
| A 单指标 | 12 | 需消歧的单步查询 | 检索 + 消歧 |
| B 对比 | 12 | 多维聚合 | 规划 + 多工具 |
| C 归因 | 14 | 多步下钻，需 ≥2 工具 | DAG + 重算 |
| D 拒答与边界 | 12 | 越权、无数据、口径不可消解、超数据范围 | 拒答准确性 |

**比对规则**

- 行序无关；键列对齐（按列名匹配，不按位置）。
- 数值容差 1e-6；字符串去首尾空格后比较；空值 `NULL` 与 `"null"` 视为不同。
- 标准 SQL 存疑的题标 `contested`，从分母剔除并单独报告数量。**contested 仅指「可执行但口径存疑」**；执行失败属题库缺陷，必须修题。

**回归门禁（合并前必过）**

| 规则 | 具体 |
|---|---|
| 固定变量 | 模型版本、prompt 版本、题库版本锁定；门禁跑分固定 `temperature=0` 以**降低**方差，但**不假定完全可复现**（批处理算子、浮点非结合性、MoE 路由都会引入差异）。同一题多次运行的差异记入 `run_variance`，它正是 9.2「同题 5 次一致率」要量化的东西 |
| 全局阈值 | 总成功率 ≥75%（80% 为加分目标，不作为阻断线）；分档门限见 9.2；未达门限不合并 |
| **零回归** | 上一基线中 PASS 的题，本次 FAIL 即阻断合并。为过滤 LLM 抖动，单题判定取 k=3 复跑，**3 次中 ≥2 次 FAIL 才计为回归**（与 9.2「5 次一致率」共用同一套多次判定规则，不另设第二套口径） |
| 配对显著性 | 新旧两次跑分在**同一批题目**上做 McNemar 精确检验：b = 通过→失败，c = 失败→通过；`p < 0.05` 且 `b > c` 判为真实退化。n=50 时检验功效有限，因此零回归是一票否决，McNemar 用于判断「整体是否真的变好/变坏」 |
| 不设固定跌幅阈值 | 50 题规模下 1 题 = 2 个百分点，用「跌幅 >3% / >5%」作唯一判据等同于掷骰子，明确不用 |
| 记录 | case 级 verdict 落盘，任意两次历史跑分可做配对比较（b/c 计数必须写进报告） |

**交互流程**

1. 加载题库（问题、标准 SQL、期望输出、所属档、是否 contested）。
2. 逐题运行 → 抓取结果集 → 与标准结果比对。
3. 输出总成功率 + 分档成功率 + 六项指标 + 失败分布。
4. 结果落盘为带时间戳的 JSON，供历史对比。
5. 与基线逐题对齐 → 零回归检查 + McNemar 精确检验 → 生成 `gate: PASS / FAIL`；FAIL 时进程返回非零退出码，CI 阻断合并。

**页面元素**

CLI 输出为主；结果同时写入看板「跑分」标签页。

**异常处理**

| 异常场景 | 处理方式 |
|---------|---------|
| 标准 SQL 本身执行失败 | 判定为**题库缺陷**，必须修题，不得记为 contested；修复前该题不参与跑分，并在报告中列为 defect |
| 被测评任务超时 | 计为失败，不重试（重试会污染统计） |
| 结果集列名与标准不一致但值一致 | 计为失败（口径不一致即错），不允许宽松通过 |

**埋点需求**

- `eval_run`：运行 ID、题目数、耗时、模型版本、prompt 版本。
- `eval_case_result`：题目 ID、档位、成功与否、指标值、失败类。
- `regression_gate`：门禁结论、b/c 配对计数、p 值、被拦截的回归题 ID 列表。

**验收标准**

- [ ] 标准 SQL **可执行率 100%**（硬要求）：50 题全部能跑出结果；执行失败按题库缺陷处理，不记为 contested。
- [ ] contested 仅用于「可执行但口径存疑」，数量 ≤3（≤6%），逐条给出裁决理由；contested 数不得随跑分结果调整。
- [ ] 同一批结果重复比对 3 次，输出的六项指标完全一致（比对器无随机性）。
- [ ] 题库中 A/B/C/D 四档题量为 12/12/14/12，与设计一致。
- [ ] 每道题都有可追溯的标准 SQL 与期望输出，缺失数为 0。
- [ ] 构造 1 道历史 PASS 题变为 FAIL 的假变更，门禁必须 FAIL 且 CI 退出码非零；构造 1 道 FAIL→PASS 的假变更，门禁必须 PASS。
- [ ] 报告必须含 b/c 配对计数与 p 值；只报告「成功率变化 X%」而不给配对检验的跑分视为不合格。

#### 6.3.15 FR-14 服务层

**需求描述**

对外 4 个接口，全部支持幂等；不做多余抽象。

| 接口 | 方法 | 用途 | 幂等 |
|------|------|------|------|

无（供前端调用）。

**异常处理**

|---------|---------|

**埋点需求**

- `api_call`：路径、状态码、耗时、是否幂等命中。

**验收标准**

- [ ] 同一幂等键 + 同参数请求 10 次，仅产生 1 次实际执行（LLM 调用次数可验证）。
- [ ] 同一幂等键 + 不同参数，返回 409 且响应体含差异字段。
- [ ] 取消已 CANCELLED 的任务，接口返回 200 且状态不变。

## 七、AI 能力定义

### 7.1 任务类型

复合型，四类能力组合：

| 能力 | 在本项目中的体现 |
|------|-----------------|
| 推理（Reasoning） | 意图解析、口径消歧、任务拆解 |
| 抽取（Extraction） | 从问句中抽取指标、时间范围、维度、过滤条件 |
| 生成（Generation） | 生成 DAG JSON、生成修复动作、生成结论文字 |
| Agent（编排） | 多步工具调用、状态保持、失败自愈、预算管理 |
| RAG（检索增强） | `metric_kb` / `task_template_kb` 混合检索 |

> 关键设计：**LLM 不输出 SQL 文本**。它输出受限的结构化参数（`metric_key` / `definition_id` / `dimensions` / `filters` / `time_range` / `order_by` / `limit`），由渲染器按 `metric_kb` 中的声明式指标定义（measure / agg / filters / dimensions / time_field）编译成 SQL。

业界三种做法的边界（本项目取第三种，不否认前两种的价值）：

| 做法 | 代表 | 适用 | 本项目是否采用 |
|---|---|---|---|
| 裸 Text-to-SQL | Vanna、SQLChat | 表结构简单、查询自由度高、可接受人工复核 | 否 |
| 语义层受控生成 | Snowflake Cortex Analyst、Databricks Genie、WrenAI | 有语义层、指标口径需治理 | 否（需额外语义层产品） |
| 参数化 / 中间表示 | dbt MetricFlow、Cube、SelectDB MCP | 指标口径固定、要求安全与可复算 | **是** |

取舍理由：本项目只有 4 个指标、10 张表，自由度换不来收益，而口径可复算与注入面收敛是面试要考的点。若未来指标数 >50 或出现临时探索式查询，再退回第一种做法并保留 Critic + 人工复核。

### 7.2 输入定义

#### 7.2.1 原始输入

| 输入 | 来源 | 形态 |
|------|------|------|
| 用户问句 | 前端输入框 / API | 中文自然语言，≤500 字 |
| 会话历史 | Redis | 结构化摘要（指标、口径、时间、维度），非原文 |
| 指标候选 | Milvus `metric_kb` | Top-5 候选定义 + 相似度 |
| 任务模板 | Milvus `task_template_kb` | Top-3 结构模板 |
| 工具 schema | 注册表 | JSON Schema |
| 基线剖面 | `metric_profile` | 指标 × 维度 × 月的 P5/P95/均值/σ |

#### 7.2.2 Prompt 结构

- **System Prompt（Planner）**：角色 = 数据任务规划器；职责 = 把问题拆成最小可执行 DAG；禁止 = 编造工具、编造参数、输出 SQL 文本、输出解释性长文；格式 = 严格 JSON，符合给定 Schema。
- **System Prompt（Critic）**：角色 = 结果审查员；职责 = 按四项检查判定；禁止 = 修改数据、给出未在证据中出现的判断；格式 = 严格 JSON 判定对象。
- **User Prompt**：问句 + 定稿口径定义（声明式字段 + 参数化渲染模板）+ 可用工具清单 + 预算余量 + 上一轮失败证据（若有）。

#### 7.2.3 上下文长度预估

| 组成 | 估算 token |
|------|-----------|
| System Prompt | 1.5k–2k |
| 工具 schema（7 个） | 1.5k–2k |
| `metric_kb` Top-5 | 1.2k–1.8k |
| 会话摘要 | 0.5k–1k |
| 工具返回摘要 | 1.5k–2.5k |
| 单次调用合计 | 6k–9k |
| 单任务调用次数 | 5–8 次（单轮，含重试）；追问类 **6–9 次**（多一次 rewrite） |
| **单任务合计** | **30k–70k** |

按双费率估算（**输出单价通常是输入的 3–5 倍，只用输入单价会系统性低估**）：输入 ¥8–12 / 百万 token、输出 ¥30–60 / 百万 token，按输出占总量 15–20% 折算，单任务 **¥0.30–0.95**。门限按模式分档（FC/ReAct ≤¥0.25、P&E ≤¥0.35、MA ≤¥0.6，见 8.3），靠「工具返回摘要化 + 关闭 rerank 降级 + 限制重试 2 次」压到线内，D10 实测确认。

## 八、模型选型与工程方案

### 8.1 模型选择

| 角色 | 选择 | 说明 |
|------|------|------|
| 主模型 | 待 D6 实测确定：候选为具备强 Function Calling 与 JSON Schema 约束能力的通用大模型（海外 / 国内各一） | 选型判据：DAG JSON 合法率、Schema 遵从率、单任务成本、P95 延迟 |
| 备用模型 | 与主模型不同厂商的同档模型 | 用于降级链第二级；必须能通过同一套 schema 契约测试 |
| Embedding | 中文语义检索表现稳定的向量模型 | 用于 `metric_kb` Dense 路 |
| Rerank | 轻量 cross-encoder | 可开关，不可用时自动跳过 |

> 不在此处写死具体型号与版本号：模型版本迭代快，写死会在面试中被追问「这个版本还支持吗」。选型结论在 D6 以实测数据形式落在 `decisions/` 目录。

### 8.2 调用方式

- 编排节点内**同步调用**（每步需结果才能继续）。
- 对外**异步任务 + SSE**（用户不必等待阻塞）。
- 评测 harness **批量串行 + 有限并发**（默认 4 并发，避免限流污染统计）。

### 8.3 性能要求

| 项 | 要求 |
|---|---|
| **P95 延迟（A/B 单轮）** | **< 10s**（不含人工澄清等待） |
| **P95 延迟（C 归因 / 追问）** | **< 20s**——追问多一次 rewrite 调用、归因多一层下钻，按同一门限要求它不现实 |
| 澄清等待 | 不计入延迟统计 |
| 并发 | 20 并发下成功率不低于单并发时的 95% |
| 日处理量 | 演示规模，无硬性要求 |
| **单任务成本 P95（分模式）** | FC / ReAct ≤ ¥0.25；P&E ≤ ¥0.35；Multi-Agent ≤ ¥0.6；**不在四模式混合样本上算一个 P95** |
| 首屏加载 | < 1.5s（本地网络） |
| 冷启动（Compose 起全套） | < 60s |

> 延迟与成本门限都按**模式/题型**分档，是因为沿用同一个数字会让 Multi-Agent 与追问题天然不可能达标——那种门限实际等于把最需要优化的场景排除在验收之外。

## 九、数据与评估体系

### 9.1 评测集

| 项 | 内容 |
|---|---|
| 规模 | 50 题（A12 / B12 / C14 / D12） |
| 来源 | 基于 11 表数据集人工设计，覆盖三组口径歧义与四类拒答场景 |
| 标注要求 | 每题必须有：问句、所属档、标准 SQL、期望输出、是否 contested、考察点标签 |
| 标准答案制定 | **双实现交叉验证**（替代单人项目无法做到的「双人独立编写」）：标准答案用 MySQL SQL 写一份，另用 DuckDB/pandas 从同一份 CSV 快照独立算一份；两份结果一致才入库，不一致进争议池由人裁决并记录理由。报告争议池触发数；为 0 时需说明为何 50 题全无分歧 |
| 争议处理 | contested 题从成功率分母剔除，单独报告数量；不得为了提高分数而随意判 contested |
| 数据集 | 11 表约 57 万行（见 4.5），脚本生成；固定随机种子，保证可复现；时间基准冻结在 `as_of_date=2026-07-01` |

**11 表清单**：`dim_merchant` / `dim_product` / `dim_category` / `dim_channel` / `dim_campaign` / `dim_date` / `fact_order` / `fact_order_item` / `fact_payment` / `fact_refund` / `fact_settlement`。粒度、主键、行数与字段见 4.5。

**三组口径歧义**

| 指标 | 争点 | 结果差异 | `metric_kb` 候选数 |
|---|---|---|---|
| GMV | 含税/不含税；含不含取消单；含不含运费 | 5–15% | ≥2 |
| 退款率 | 按单/按金额；是否含售后期 | 可差 1 倍 | ≥2 |
| 客单价 | 按支付金额/按下单金额；是否含退款 | 10%+ | ≥2 |

### 9.2 评估维度与验收标准

| 维度 | 评估方法 | 验收标准 |
|------|----------|----------|
| **准确性** | 结果集与标准 SQL 结果逐格比对（行序无关、键对齐、容差 1e-6、字符串去空格）；D 档按「拒答且理由正确」判定；另统计首轮 SQL 正确率与消歧正确率 | 任务成功率 ≥75%（D20 门限 60%，D25 门限 75%；80% 为加分目标）；D 档拒答正确率 ≥85%；首轮 SQL 正确率 ≥65%；消歧正确率 ≥90% |
| **完整性** | 输出是否覆盖题目要求的全部维度、指标与时间粒度；多步题是否给出中间下钻过程 | 完整性 ≥85%；漏维度/漏指标计为失败，不做部分给分 |
| **稳定性** | 同题重复 5 次的一致性（各次结果完全相同）；20 并发下的成功率；P95 延迟 | 同题 5 次结果一致率 ≥90%；20 并发成功率 ≥单并发的 95%；P95 延迟按题型分档（见 8.3） |
| **数值幻觉率** | 输出中每个数字与工具返回值做指纹比对，**全自动判定、可作门禁** | 无依据数值占比 ≤2%；出现即判 HALLUCINATION 且不回灌重试 |
| **结论幻觉率**（观测项，不设门禁） | 结论文字中的因果断言是否引用了未出现的证据——纯语义判断，需人工或判定模型打分，n=50 的样本推不出百分比门限 | 只报告「抽检数 / 检出数 / 逐条理由」，不设硬门限；连续两轮检出即触发一次全量复核 |

**分档门限（辅助指标）**

| 档 | 目标成功率 |
|---|---|
| A 单指标 | ≥90% |
| B 对比 | ≥80% |
| C 归因 | ≥65% |
| D 拒答与边界 | ≥85%（拒答正确率） |

> 分档门限为调优方向，不替代总成功率的验收地位。

> 回归判定不设固定跌幅百分比：50 题规模下 1 题 = 2pp，改用「零回归 + McNemar 配对检验」，规则见 6.3.14。

### 9.3 评测算力预算

评测本身是 LLM 调用大户，必须单独预算，否则调优期会被费用和限流反噬。

| 场景 | 触发时机 | 运行次数 | 单次成本 | 小计 |
|---|---|---|---|---|
| 首轮跑分 | D19 | 50 题 × 4 模式 = 200 | ¥0.3–0.8 | ¥60–160 |
| 增量门禁（默认） | 每次改动 / 每日调优 | 受影响题型 ≈15 题 × 部署模式 1 × k=3 = 45 | ¥0.3–0.8 | ¥14–36 |
| 全量门禁 | D20 / D25 / D30 三次 | 50 × 4 × k=3 = 600 | ¥0.3–0.8 | ¥180–480 |
| 稳定性（5 次复跑） | D25 一次 | 50 × 1 模式 × 5 = 250 | ¥0.3–0.8 | ¥75–200 |
| **合计** | — | — | — | **¥330–880**（调优期 4 天按增量门禁计） |

**降本手段**（按优先级）：

1. 日常回归只跑**受影响子集**：改消歧规则 → 只跑 B/C 档；改 Prompt → 只跑触发该角色的题型。全量门禁只在三个节点跑。
2. 门禁期间**关闭 rerank 与 Multi-Agent 模式**：对比表只在全量门禁产出，日常不重算四模式。
3. `k=3` 只对**与变更相关**的题复跑；未触碰的题沿用上一轮结果。
4. 工具返回摘要化 + 限制重试到 2 次（与 7.2.3 的成本目标同源）。

> 门限不变：省的是运行次数，不是判定严格度。全量门禁的 600 次运行不可省。

## 十、Prompt 与规则设计

### 10.1 System Prompt 核心要素

以 Planner 为例，四要素必须齐备：

1. **角色定义**：你是电商经营分析的查询规划器，只负责把问题拆成工具调用图，不负责回答。
2. **任务定义**：输入为问句 + 已定稿口径 + 工具清单；输出为 DAG JSON。
3. **输出格式**：严格 JSON，符合给定 Schema；不得输出 Markdown 代码块以外的任何文字。
4. **约束条件**：
   - 工具必须来自给定清单，不得虚构。
   - 参数必须符合对应 schema，不得留空占位。
   - 禁止输出 SQL 文本；SQL 由系统按模板渲染。
   - 节点数 ≤8；无环；依赖必须存在。
   - 拿不准时选择「少拆一步」而不是「猜测参数」。

Critic 的 System Prompt 同样四要素，但约束为：只依据给定证据判定；证据不足时判 REJECT 而不是猜测通过；不得修改任何数据。

### 10.2 规则注入方式

| 规则类型 | 注入方式 | 原因 |
|---|---|---|
| 指标口径 | RAG 检索注入（`metric_kb` Top-5） | 口径会随业务变，不能硬编码进 Prompt |
| 工具清单与参数 schema | 每次调用从注册表动态注入 | 工具变更不需要改 Prompt |
| 失败修复经验 | 结构化回灌（上一轮证据对象） | 避免自然语言对话污染判定 |
| 安全红线（只读、禁 SQL 生成） | 硬写入 System Prompt + 代码层兜底 | Prompt 注入不可靠，必须代码双保险 |
| 输出格式 | JSON Schema + 服务端校验 | 校验失败可重试，不依赖模型自觉 |

### 10.3 Few-shot / CoT

| 角色 | 策略 |
|---|---|
| Planner | Few-shot：3–5 个 DAG 示例，覆盖「单指标 / 多维对比 / 归因下钻 / 应拒答」四类；示例只给结构，不给答案数值 |
| Critic | CoT：先列证据再给判定，但**最终输出必须是结构化 JSON**，CoT 只在 `evidence` 字段内体现 |
| Executor | 无 CoT（工具调用不需要） |
| 结论生成 | 轻量 CoT：先写「数据事实」，再写「可能解释」，最后显式标注「解释未经因果验证」 |

> 反模式：让 Critic 与 Planner 自由对话「讨论哪里错了」。这会引入上下文污染，且无法单测。

### 10.4 Prompt 版本管理

- Prompt 与 schema 同仓管理，目录 `prompts/{role}/v{n}/`。
- 每次改动必须附：改动理由、影响范围、回归结果（50 题逐题 verdict + 配对 b/c 计数）。
- 跑分结果 JSON 中记录 `prompt_version` 与 `schema_version`，保证历史结果可追溯。
- 回滚判据：零回归检查不通过（任一历史 PASS 题复跑 3 次中 ≥2 次 FAIL），或 McNemar 判为显著退化（`p<0.05` 且 `b>c`），直接回滚。不设固定跌幅百分比阈值。

## 十一、兜底与风控

### 11.1 格式异常兜底

| 层级 | 措施 |
|---|---|
| L1 | 启用 JSON Schema 强约束（structured output / json_schema 模式） |
| L2 | 解析失败 → 尝试提取首个合法 JSON 块 |
| L3 | 仍失败 → 附上校验错误让模型重生成 1 次 |
| L4 | 仍失败 → 降级到简化 schema（**仅保留 node_id / tool / args / depends_on**；只砍 `expected_output` 与可选字段）。`depends_on` 是四个字段里语义最关键的，砍掉会让 DAG 退化成无序列表，拓扑序不变量被兜底自己破坏 → 产物仍须过无环校验；成环或节点数 >8 则直接 L5 |
| L5 | 仍失败 → 任务 FAILED，失败类 `PLAN`，不进入执行 |

### 11.2 低置信处理

- 检索 Top1 相似度 < 0.72（阈值待 D9 实测校准）→ **不猜**，直接进入澄清。
- Top1 与 Top2 差值 < 0.02 → 视为并列，强制澄清。
- 澄清批次用尽 → 未定稿项取场景默认口径，输出顶部逐项标注「口径为系统默认」。
- 口径不可消解（问句自相矛盾 / 超出数据范围）→ 拒答并给出原因与支持范围。
- 禁止行为：低置信时静默取一个口径出数。

### 11.3 幻觉防控

| 手段 | 说明 |
|---|---|
| 数值指纹 | 输出中每个数字必须在工具返回值中出现（容差 1e-6）；未命中即判 HALLUCINATION |
| 禁止心算 | 所有比率、环比、占比、贡献度必须走 `sandbox_calc`，不允许 LLM 直接计算 |
| 口径可溯 | 结果区必须展示所用 `definition_id` 与其 SQL 片段；无溯源即不可交付 |
| 结论限定 | 结论文字必须区分「数据事实」与「可能解释」，后者显式标注未经验证 |
| 不做无限重试 | 判 HALLUCINATION 后直接 REJECT，重试只会再次编造 |
| 抽查机制 | **每次全量跑分后**人工抽查 20 条 COMPLETED 任务（A/B/C/D 四档各 5 条），核对数值与标准 SQL；数值类幻觉发现 1 条即触发全量回归，结论类幻觉记录理由并累计 |

### 11.4 安全合规

| 项 | 措施 |
|---|---|
| 数据 | 全合成，无姓名/手机号/地址/证件号；商家为虚构企业名 |
| 访问 | DB 只读账号，权限最小化；启动时 fail-fast 校验 |
| 注入 | LLM 不产出 SQL 文本；参数化绑定；渲染后用 sqlglot 做 AST 节点白名单校验；DB 只读账号兜底 |
| 越权 | 单机演示无多租户；预留 `X-Tenant-Scope` 透传位，不启用鉴权（待确认） |
| 审计 | 每次工具调用写 `audit_log`（任务、工具、参数形状、状态），不含结果内容 |
| 留存 | 日志 30 天，审计表本地长期保留 |
| 第三方 | LLM 调用外发内容仅含问句、口径定义、工具 schema 与结果摘要；不含结果明细与任何业务数据行 |
| 输入侧 | 用户问句在送 LLM 前做命中检测：手机号 / 邮箱 / 证件号正则**只在此处用于告警与脱敏**（不作为 SQL 安全边界），命中即脱敏后再外发并记一条审计 |
| 数据出境 | 本项目全部为合成数据、无个人信息，接入的为境内模型 API，**不构成数据出境**；若后续换用境外厂商，须先做供应商数据使用条款（是否用于训练、留存期、删除机制）书面确认 |
| 法务评审 | **未走法务/合规评审**（个人作品集项目，无企业主体流程）。上述结论为作者自评估，README 中如实标注这一点，不写成「已通过合规评审」 |

## 十五、风险评估

| 风险类型 | 风险描述 | 影响程度 | 应对措施 |
|---------|---------|---------|---------|
| 技术风险 | LLM 输出不稳定，DAG 合法率低导致成功率上不去 | 高 | JSON Schema 强约束 + 结构校验重试 + 降级到简化 schema；D20 门限不达标则冻结新功能只调优 |
| 技术风险 | 50 题标准答案本身有争议，导致指标失真 | 中 | SQL + DuckDB/pandas 双实现交叉验证 + 争议池 + contested 剔除并单列报告；禁止为提分滥标 contested |
| 技术风险 | 单任务成本超出分模式门限（FC/ReAct ¥0.25、P&E ¥0.35、MA ¥0.6） | 中 | 工具返回摘要化、关闭 rerank 降级、限制重试次数、收窄任务范围（见 11.2）；D10 实测校准 |
| 技术风险 | Milvus 资源占用导致本机跑不动 | 中 | 接口级抽象，D27 验证 pgvector 降级路径 |
| 业务风险 | 只做 demo 不打分，面试被追问即失效 | 高 | 训练集/评测集分离；D20/D25 两轮硬门限；指标必须可现场复算 |
| 业务风险 | 被质疑「多 Agent 是为多而多」 | 高 | 三角色只传结构化产物 + 独立单测 + 四工作流对比表用数据回答 |
| 资源风险 | 30 天排期紧，功能蔓延 | 高 | 明确「不可砍」与「可让」清单；任何新增需求必须置换掉一个可让项 |
| 资源风险 | 单一 LLM 供应商限流 | 中 | 主备双厂商；评测记录模型版本 |
| 合规风险 | 资金相关数据引发误读 | 低 | 全合成数据；README 与页面明确标注「合成数据，非真实交易」；不涉及真实资金流 |
| 合规风险 | 数据泄露 | 低 | 无 PII；LLM 外发内容不含结果明细；审计只记形状不记内容 |
| 合规风险 | SQL 注入导致数据被篡改 | 低 | 只读账号 + 参数化渲染 + AST 节点白名单 + 表白名单 + fail-fast 权限校验 |
