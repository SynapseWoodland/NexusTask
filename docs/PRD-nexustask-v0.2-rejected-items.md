- 对应评审：`analysis/2026-11-05-prd-review-nexustask-v0.1.md`（4.4/10，不合格）

## 二、逐项说明

### R1｜角色类必填项（设计师 / PM / 技术负责人 / 测试主R / 需求提出人 / tapd）

**评审原文依据**：模块 1 表，11 项中缺 7 项，小计 -2.0 触顶归零。

**不采纳理由**：
1. 这 6 个字段是**组织协作的接口**，不是需求内容。单人项目里造人名等于在文档里伪造组织关系，比留空更糟——面试官看到"测试主R：张三"而项目只有一个人，第一反应是这份文档是套模板生成的。
2. 本项目的读者只有两类：**未来的自己**（半年后回看设计决策）和**面试官**（看系统设计能力）。二者都不需要知道"谁是 PM"。
3. 评审自己也承认这属"模板结构性不适配"，并在 §八 做了折算——说明这是模板与场景的错配，不是文档缺陷。

**替代处理（已写入 v0.2 §0）**：

| 原字段 | v0.2 写法 |
|---|---|
| 设计师 / 设计稿 | 无。前端为自用 demo 单页，**无需设计稿** |
| PM / 技术负责人 / 测试主R / 需求提出人 | 本人（一人承担全部角色） |
| tapd / 需求管理地址 | 无。版本管理见修订记录 + git |

**将来若转公司立项需补**：填入实名 + 建 tapd 需求单 + 挂设计稿链接。这一步是流程动作，不是内容动作，随时可补，不构成设计负债。

---

### R2｜灰度方案 + 回滚预案

**评审原文依据**：模块 5，未标注"无需灰度"，扣 0.2；另指出"全文无回滚预案"。

**不采纳理由**：
1. 灰度的定义是"向部分线上用户放量并观察指标"。本项目**没有线上用户**，灰度无对象。
2. 回滚预案同理：没有已发布的版本，就没有"回滚"这个动作。把 git 恢复写成"回滚预案"是文字游戏。
3. 评审建议的"数据集脚本化可重建"是对的，但它属于**数据可复现性**，已在 §6.3「配套产物随数据集版本化」中覆盖，不需要单开一节。

**替代处理（已写入 v0.2 §0）**：一行声明"无需灰度。无生产流量；§8 的 A/B/C/D 四模式离线对比为等效评估"。

**将来若转公司立项需补**：灰度范围（按用户 ID 尾号 / 按门店）、放量比例（1% → 5% → 20%）、观察指标（成功率、P95、成本）、回滚触发阈值。

---

### R3｜为"50 并发"补容量工程（RPM/TPM、多 Key、限流分层）

**评审原文依据**：P1-1——单任务 8–15 次模型调用，50 并发 ≈ 400–750 RPM，供应商配额、限流降级全空白。

**部分不采纳。** 评审的诊断是对的，但处方错了：

- **诊断成立**：50 并发确实换算后与个人 API 配额不匹配，这个声称撑不住。
- **处方不成立**：正确解法不是"补一套 RPM 配额管理与多 Key 降级"，而是**把声称降到能证明的水平**。个人项目去做多供应商限流分层，投入产出比极低，而且多出来的工程也不会被问到——面试官问的是"你怎么设计可扩展"，不是"你的 key 配额多少"。

**替代处理（已写入 v0.2）**：
- NFR-04 从"50 并发不降级"改为 **"20 并发不出现任务串号与丢失"**，验收判定为"成功率不下降"
- 补了评审真正要的**容量口径**：单任务模型调用次数上界约 10 次，20 并发峰值 ≈ 200 次调用 / 任务平均时长（§5 NFR-04 备注）

**这样改的收益**：声称从"不可验证"变成"可验证"，且 20 并发已经足以证明"无状态 worker + Redis 外置状态"的可扩展设计——这本来就是该证明的东西。

**将来若转公司立项需补**：目标 QPS/RPM、供应商配额、限流触发的排队策略、多 Key 轮转。

---

### R4｜补业务量化数据（"月均影响 5 万用户、转化率下降 15%"）

**评审原文依据**：模块 2，量化数据为零，扣 0.5。

**部分不采纳。** 拆成两半看：

- **"缺问题陈述"成立** → 已在 v0.2 §2.0 补上（用户 / 场景 / 问题 三条），这条我认。
- **"必须有真实业务量化数据"不成立** → 个人项目没有真实用户，编一个"月均 5 万用户受影响"就是造假。评审给的示例本身是借款业务的真实数据场景，与本项目不可比。面试官若追问"这 5 万从哪来的"，答"我假设的"，前面的可信度全搭进去。

**替代处理（已写入 v0.2 §2.0）**：
- 加**显式假设声明**："本节数字为界定场景规模的假设参数，不来自任何真实企业。项目不依赖这些数字成立。"
- 保留具体数值（15 人团队 / 5 亿 GMV / 200 次临时取数 / 30% 工时 / 2 天等待 / 15% 口径偏差），但整体框定为假设
- 补了评审真正的追问点：**"为什么不用 Metabase"**（§2.0 末段）

**这样处理的逻辑**：诚实标注的假设 > 无数据 > 伪造数据。面试时"这是参考场景，参数是我设的"是可接受的回答；"这是我调研的"被追问就崩。

---

### R5｜"模块 1 归零 → 整体不合格"的计分口径

**不采纳的是计分方式，不是结论。**

- 模块 1 的 1.0 分里，约 0.8 分来自单人项目不存在的组织字段。用"缺 7 项扣到归零"的方式计算，会让一个内容质量 5.5–6.0 的文档显示为 4.4，**误导改进优先级**——它会让人先去补人名和 tapd 链接，而不是去补评测口径。
- 评审自己在 §八 已给出折算分（4.6），但折算口径只调整了模块 1，没有调整模块 5/6/7 的模板项，所以仍是低估。

**替代处理**：v0.2 不追 7.0 合格线。理由：这套模板的 7 分是给"有 PM、有灰度、有资金流水"的公司立项文档设计的，追它等于往文档里塞僵尸章节（比如编造灰度方案、编造资金风险等级），反而降低文档可信度。

**真实的质量判据应该是什么**（v0.2 采用）：
1. 每个 P0 需求是否有**可判定的验收标准** → 是
2. 关键设计决策是否有**换回触发条件** → 是（§7）
3. 评测指标是否有**明确定义** → 是（§8.1）
4. 失败能否被**自动归类** → 是（§5 FR-11 六类）
5. 排期是否有**可验证的日级收工状态** → 是（§9）

## 四、一句话

不采纳的 5 项，全部是"组织流程类字段"和"个人项目拿不出的业务数字"——前者是模板与场景的错配，后者是造假比留空更伤可信度。v0.2 对每一项都给了等效处理（一行声明或降级声称），因此文档里**看不到空白格，但也不会出现编造的内容**。
