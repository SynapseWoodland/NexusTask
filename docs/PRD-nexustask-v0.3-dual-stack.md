## 0. 本版相对 v0.2 的三个决定

### 0.1 决定一：业务域定为「SaaS 计费 + 风控」

先回答那个悬着的问题——**"数据集用电商还是你的老本行"到底在问什么**。

这是 v0.2 §6.3 的一个阻塞项：项目要自建 10 张表才能演示"口径歧义 + 多步归因"，但表结构长什么样，取决于模拟哪个行业。三个选项：

| 选项 | 好处 | 坏处 | 判定 |
|---|---|---|---|
| 电商 | 数据集好造，退货率歧义好讲 | 烂大街；和你的经验无关；**没有"钱"**，写操作与审批设计无处落脚 | 弃 |
| 车企/制造 | 故事贴合"传统行业转型" | 你没有行业知识，任何追问都会露馅 | 弃 |
| **SaaS 计费 + 风控** | **你的 3 年真实经验**；计量、账单、退款天然涉及"钱"；口径歧义是这行的日常争吵；两个服务（计费 + 风控）天然跨系统 | 需要多花半天做领域建模 | **选** |

**最关键的理由不是"熟悉"，是"可辩护"**。评审 P0-3 指出：v0.2 把"口径歧义"当成立论基础，却又说不清歧义从哪来。用 SaaS 计费，这个问题自动消失——因为你能不假思索地答出"ARR 到底含不含税、按不按合同期年化"，而且答得比面试官细。**这是 3 年经验唯一无法被 AI 替代的部分。**

### 0.2 决定二：Agent 之外，手工实现一套「存量 Java 系统」

不是再写一个 CRUD 玩具，而是**刻意复刻存量系统的坏毛病**：

- HTTP 一律 200，错误藏在业务码里（`B2001`）
- 金额单位是"分"（long），时间是 `yyyyMMdd` 字符串
- 分页强制 `pageSize ≤ 100`，没有游标
- 退款要 `Idempotency-Key`，重放返回同一结果
- 只有业务视角接口，没有"给 Agent 用"的聚合接口
- 权限只到租户级，没有字段级

**为什么故意留坑**：这七个坑就是网关存在的理由。没有它们，网关只是一个转发器；有了它们，网关一次调用要做 分页聚合 + 错误码归一 + 单位换算 + 幂等透传 + 行级过滤，才有工程量可讲。

**必须对面试官说清楚**：这是**模拟**，不是任何真实企业系统。模拟的价值在于约束真实，不在于数据真实。

#### 0.2.1 对外口径：卖点是"你不能改"，不是"它很老"

| 说法 | 真实性 | 风险 |
|---|---|---|
| "这是个跑了十年的老系统" | 假 | `pom.xml` 一看是 Boot 3.5，问一句 JDK 就穿帮 |
| "我按存量系统的约束做了个仿真" | 真 | 无，而且能顺势展开 7 条约束 |
| **"这是一个我无权修改的第三方系统"** | **真**（组织边界意义上） | 无，**推荐** |

核心不是"老"，是**"你没有修改权"**。这个说法 100% 诚实，杀伤力一点不降。

四个让仿真站得住的动作：

1. **双仓库分离**：`billing-platform`（对方）与 `nexustask-agent`（我方），契约打 tag `contract-v1.0`
2. **契约先冻结**：Java 侧 PRD 已落盘（`D:\github\SAAS-billing\PRD-saas-billing-platform-v1.0.md`），§8.1 的 7 条硬约束与 §14 冻结声明不可协商；该 tag 的 commit **早于** Agent 首个 commit（`git log` 可证）
3. **Agent 侧不得为适配而改 Java**：所有差异在网关消化，Java 仓库全程零 Agent 相关提交
4. **演示契约变更**：改一版接口 → 网关 manifest diff 告警，证明它真的被当作外部系统对待

一句话口径：**"数据是生成的，系统是仿真的，约束是照着真实系统抄的。"**

### 0.3 决定三：引入写操作，但只开一个口子

v0.2 写的是"只读，无 DML"。本版**必须改**——如果系统只读，那么"安全治理"就是空话：只读系统最坏结果是查错数，谈不上授权、审批、回放。

但写操作只开**一个不可逆口子**：

| 等级 | 工具 | 语义 | 保护 |
|---|---|---|---|
| READ | 11 个查询类 | 只读 | 行级过滤 + 审计 |
| WRITE_REVERSIBLE | `create_credit_note` | 生成草稿贷记单，可作废 | 审计 + 幂等 |
| WRITE_IRREVERSIBLE | `create_refund` | 发起退款 | dry-run + **人工审批令牌** + 金额上限 ¥5,000 + 每任务最多 1 次 + 幂等 |

一个口子足够证明整条链路，又不会把项目做成支付系统。

## 1. 选题结论：为什么是"准入网关"

### 1.1 三个候选，只留一个

| 候选 | 描述 | 问题 |
|---|---|---|
| A. 再做一个 Agent 框架 | 复刻 LangGraph/ReAct | 重复造轮子，且 JD 要的是"会用"不是"会造" |
| B. 纯 Python 取数 Agent（v0.2） | 只连自建 MySQL | 能证明 Agent 深度，但**"集成"这一维完全空缺**，而 JD 职责 3 整条讲的就是与外部系统交互 |
| C. Python Agent + 准入网关 + 存量 Java 系统 | 三层 | 工期多 3 天，但一次性覆盖 JD 职责 1/2/3/4 与加分项 2/4 |

**选 C**。理由不是"看起来更全"，而是：**JD 职责 3 写的是"开发 Agent 与外部系统（如 API、数据库、知识库、RAG）的安全、高效交互机制"**。v0.2 只做到了"数据库"这一种，且是裸连。"安全"和"高效"两个词，v0.2 都没有真正的载体。

### 1.2 差异点不在"能对接"

调研结论很明确：Python Agent 调 Java 接口是 2026 年的默认分工，MCP 让工具层与语言脱钩，**"能对接"没有壁垒**。

壁垒在四件事上，而协议层一件都不管：

| 问题 | 谁来管 |
|---|---|
| 模型能不能拿到数据库账号密码？ | 凭据持有与代调用 |
| 这次任务能调哪些工具、能看哪些租户？ | 意图级授权、行级过滤 |
| 退款这种操作谁能批、怎么防重放？ | 审批令牌、幂等、dry-run |
| 三个月后出事，能否说清哪一步、哪个数据源？ | 审计链、脱敏、trace 关联 |

**产品定义由此收敛为一句话**：让 Agent 能安全操作一个它改不动的系统。

## 2. 业务场景

### 2.0 Java 服务在做什么：一条 SaaS 计费闭环

```
签约 → 订阅(套餐/坐席) → 每月出账 → 收款 → 逾期催收 → 退款/减免
                    ↑ 风控在 签约 / 续费 / 退款 三个节点介入
```

| 服务 | 负责什么 | 本次用到 |
|---|---|---|
| `billing-service` :8081 | 租户、套餐、订阅、账单、明细、收款、退款、贷记单 | 8 张表 + 10 个接口 |
| `risk-service` :8082 | 风控规则、命中记录、租户风险分 | 3 张表 + 3 个接口 |

> Java 侧需求文档：[PRD-saas-billing-platform-v1.0.md](file:///D:/github/SAAS-billing/PRD-saas-billing-platform-v1.0.md)。**Agent 侧不得修改它**，所有差异在网关消化。

Agent 的业务价值只有三件事：**查得准**（口径对）、**算得对**（跨系统聚合）、**动得安全**（退款要审批）。

### 2.1 假设声明

> 以下数字为界定场景规模的**假设参数**，用于说明量级，**不来自任何真实企业**，项目不依赖其成立。面试时须主动声明（评审拒绝项 R4 的教训：编造业务数据比留空更糟）。

- 客户：一家 B2B SaaS 公司，约 800 家企业租户，4 条产品线，年 ARR 约 1.2 亿
- 角色：财务 BP、客户成功（CS）、销售运营
- 系统现状：计费系统与风控系统是两套独立 Java 服务，各有各的数据库，互不打通

### 2.2 问题

1. **取数要排队**：财务/CS 每周约 60 次临时取数与对账请求，平均等 1–2 天
2. **同一指标三个数**：ARR、流失率、逾期率各有 2–3 种口径，月会先花 20 分钟对数
3. **跨系统操作靠人肉**：判断一个租户能不能退款，要查计费（是否已开票）+ 风控（是否命中规则）+ 合同（是否在锁定期），再走邮件审批，平均 2.5 天
4. **没人敢让 AI 直接动钱**：此前试过让 AI 生成退款申请，因无法回答"它凭什么动这笔钱"而搁置

### 2.3 三组口径歧义（这是项目的立论基础）

| 指标 | 争什么 | 候选口径 |
|---|---|---|
| **ARR** | 含税还是不含税？按当前 MRR×12 还是按合同期年化？试用期算不算？ | 3 条 |
| **流失率** | 按客户数还是按 MRR？主动取消还是到期未续？降级算不算流失？ | 3 条 |
| **逾期率** | 按账单笔数还是按金额？D0 还是 D30？争议账单剔不剔除？ | 3 条 |

每组至少 2 条候选存入 `metric_kb`，**没有任何一条被标为"唯一正确"**——这正是 v0.2 评审 P0-3 要求补上的"一对多 + 消歧策略"。

> 为什么这组歧义比"退货率按单还是按件"更好：它不只是定义之争，**还会改变 SQL 的聚合粒度与连接方式**（按金额 → `SUM(amount)`；按笔数 → `COUNT(DISTINCT invoice_id)`），所以检索错必然导致结果错，RAG 的必要性是真的。

**"口径"到底指什么**——同一个指标名，业务上有多种算法；不先选定一种，数就出不来：

```sql
-- 逾期率（按金额）  金额口径：大客户一逾期就把整体拉爆
SELECT SUM(amount_cents) FILTER (WHERE status='OVERDUE')
     / SUM(amount_cents) FROM invoice;

-- 逾期率（按笔数）  笔数口径：小客户逾期多，比例反而高
SELECT COUNT(*) FILTER (WHERE status='OVERDUE')
     / COUNT(*) FROM invoice;
```

两种都合理，同一份数据能差 3 倍。**选错口径 → 聚合粒度错 → 结果错**，这就是 `metric_kb` 必须返回候选集、而不是返回唯一答案的原因。

**面试怎么讲**：财务看金额、CS 看笔数，月会吵的就是这个。这不是编出来的歧义，是 SaaS 公司每月都在发生的事。

### 2.4 量化目标（工程口径，不是业务吹牛）

| 目标 | 指标 | 门限 |
|---|---|---|
| 取数自动化 | 50 题评测成功率 | ≥ 80% |
| 口径一致性 | 消歧正确率（人工判定） | ≥ 90% |
| 安全 | 越权调用拦截率 | **100%**（硬门限） |
| 安全 | 未审批的不可逆写操作执行次数 | **0**（硬门限） |
| 安全 | 写操作重复执行次数 | **0**（硬门限） |
| 成本 | 单任务 token 成本 | ≤ ¥0.5 |
| 延迟 | P95（不含人工审批等待） | < 15s |

## 3. 产品定义

### 3.1 一句话

用户用自然语言提出计费/风控相关的取数或操作请求，系统澄清歧义、拆解任务、检索口径、编排跨系统调用、自检结果；**所有对 Java 系统的调用都经准入网关，凭据不进模型、写操作需人工审批、全过程可回放**。

### 3.2 端到端主流程

```
用户提问
  │
  ├─[1] 接入层     生成 task_id，幂等键去重 ──────────────── 用户可见：任务卡
  │
  ├─[2] 澄清      口径歧义 / 指代不明 / 范围过大 / 越权意图 ─ 用户可见：候选口径卡片(≤2轮)
  │
  ├─[3] 规划      输出 TaskDAG（步骤 + 依赖 + 验收条件）──── 用户可见：计划列表
  │
  ├─[4] 检索      metric_kb 返回候选集 → 五级消歧 ────────── 用户可见：选中口径 + 理由
  │
  ├─[5] 执行      经网关调 Java 系统（READ）─────────────── 用户可见：SSE 进度流
  │      │
  │      └─ 若含 WRITE_IRREVERSIBLE：
  │           dry-run → 展示影响 → **人工审批卡片** → 审批令牌 → 执行
  │
  ├─[6] 校验      Critic 四类检测 + 基线剖面比对 ─────────── 用户可见：异常提示或重算
  │
  └─[7] 输出      表格 + 图 + 口径说明 + 数据来源 + 成本 ─── 用户可见：结果页 + 可下载
```

### 3.3 明确不做

- 不做通用 Agent 平台（只服务这一套模拟系统）
- 不做多租户 SaaS 化（单实例 demo）
- 不做模型微调
- 不做真实支付通道（退款只在模拟库内改状态）
- 不做自由对话的多 Agent（沿用 v0.2 §1.3 硬约束：只传结构化产物）
- 不做前端产品化（单页 + SSE + 审批卡片）

## 5. 架构

### 5.1 三个平面

```
┌─────────────────────────────────────────────────────────────┐
│  接入 / 交互      单页（SSE + 审批卡片）                      │
└───────────────────────────┬─────────────────────────────────┘
                            │ HTTPS / SSE
┌───────────────────────────▼─────────────────────────────────┐
│  A. Agent Runtime（Python 3.11，本项目主战场）                │
│     FastAPI · LangGraph 10 态 · Redis checkpoint             │
│     Planner / Executor / Critic（结构化通信）                 │
│     metric_kb(Milvus) · 四工作流 · 预算 · Langfuse            │
└───────────────────────────┬─────────────────────────────────┘
                            │ MCP over Streamable HTTP（只出站）
┌───────────────────────────▼─────────────────────────────────┐
│  B. Access Gateway（Python，本项目的差异点）                  │
│     OpenAPI → Tool Manifest · 契约归一化 · 三级风险            │
│     意图级授权 · 凭据保管 · dry-run · 审批令牌 · 审计 · 脱敏   │
└───────────────────────────┬─────────────────────────────────┘
                            │ REST（既有接口，零改造）
┌───────────────────────────▼─────────────────────────────────┐
│  C. Legacy Java（Spring Boot 3.5 / JDK 21，故意留坑）         │
│     billing-service :8081  ·  risk-service :8082             │
│     MySQL · Redis · HTTP 200 + 业务码 · 金额单位=分            │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 为什么是三层而不是两层

如果把网关合进 Agent Runtime，会得到一个致命问题：**凭据与推理在同一个进程里**。那么"模型拿不到数据库密码"只能靠 prompt 约束——等于没有约束。

物理隔离之后，边界是进程边界 + 网络边界：
- 模型上下文里只有工具名、参数、返回值摘要
- 凭据只存在于网关进程的环境变量 / 密钥文件
- 网关是唯一能连 Java 服务的组件（网络策略上，Agent Runtime 不可直连 8081/8082）

**这一条是整份设计的支点，也是面试时最容易被追问的地方**（见 §14 第 3 问）。

### 5.3 部署

| 环境 | 形态 |
|---|---|
| 开发 | Docker Compose：mysql / redis / milvus / billing / risk / gateway / runtime / web |
| 演示 | 同上 + 预置数据集，`make demo` 一条命令起 |
| K8s | manifests（Deployment + Service + HPA 配置），**不实跑 HPA**，理由见 §12 |

## 6. 关键设计决策

每条含：决策 / 理由 / 替代方案 / 换回条件。这一节是为了应对"为什么不用 X"的追问（沿用你的一贯要求）。

### 6.1 决策 D1：Agent 在 Python，业务在 Java

- **先排除一个错误理由**：不是"Java 做不了 Agent"。AgentScope Java 2.0（2026-07 GA）只要 **JDK 17+**、不依赖 Spring Boot、可独立部署；LangChain4j 同理。也就是说，**旁路部署一个 Java Agent 服务，存量系统一行都不用改，运行时也不是障碍**。
- **真正的约束在部署形态**：

| 部署形态 | 能不能用 Java Agent 框架 | 代价 |
|---|---|---|
| 旁路（独立容器 + 自带 JDK 17） | 能，AgentScope / LangChain4j 都行 | 多维护一套 JVM 服务；评测/RAG 生态较弱 |
| 同进程（写进原应用，复用 Bean/事务/安全上下文） | 取决于原应用版本 | JDK 8/11 的存量系统装不上（Record/Sealed Class）；Spring AI 2.0 还要 Boot 4 / JDK 21 |

- **本项目的真实选择理由（三条，按权重）**：
  1. **物理载体**：整份设计挂在"10 态显式状态图 + 节点级 checkpoint + 审批中断"上。LangGraph 原生提供；AgentScope 是 ReAct + Pipeline/MsgHub 范式，没有图级 checkpoint 与 `interrupt_before`，要用它就得自己把状态机再造一遍。
  2. **评测与可观测**：Langfuse 的 dataset / experiment / trace 回放是 Python 侧，§11 的 50 题 × 4 模式跑批直接建在上面。
  3. **JD 匹配**：JD 点名 Python 与 LangChain 系；Java 是加分项不是入场券。
- **替代方案与换回条件**：
  - 全 Spring AI 2.0：仅在"新建系统 + 团队纯 Java + 允许 JDK 21"时更省事。
  - 全 AgentScope Java 2.0：在"客户禁止引入 Python 运行时 + 已具备 JDK 17 容器平台"时是最现实的替代。**换回触发条件**：若我方不允许部署 Python 运行时，且状态机可退化为 ReAct + 编排模板，则整体平移；届时 §5 三层结构不变，只换最上层运行时。
- **面试口径**：不要说"Java 不成熟"。要说"三条路我都看过，AgentScope 是可行替代，但它不是图状态机范式，我这套设计要的东西它得自己造"。

### 6.2 决策 D2：不改 Java 一行代码，只读 OpenAPI

- **理由**：调研原话——"若要求'先改造系统再接入'，项目基本推不动；能在不改造前提下通过界面层或接口层完成对接，才是真正能落地的方案。"
- **做法**：网关读 `openapi.json`，生成 Tool Manifest，把 13 个 REST 接口变成 13 个工具。
- **替代方案**：让 Java 侧加 `@McpTool`（Spring AI 2.0）。技术上更干净，但**需要改对方代码 + 升级运行时**，正好踩中企业最忌讳的两件事。
- **边界**：不是所有系统都有 OpenAPI。**没有 API 的系统（老 ERP/单机软件）不在本版范围**，只在 §13 列为降级方向（只读库视图 / RPA）。

### 6.3 决策 D3：凭据只存在于网关

- **理由**：prompt injection 的最终形态是"让模型把凭据吐出来"。只要模型上下文里没有凭据，这条路就断了。
- **做法**：
  - Java 服务只认一个 service account（网关持有）
  - 模型看到的工具签名里只有 `tenant_id` 之类的业务参数，没有 token
  - 网关按"意图上下文"改写请求：注入租户过滤、注入审计头、限制分页大小
- **替代方案**：给每个用户发 token 透传给 Java。**不可行**：Java 侧权限只到租户级、且不能改，用户级细粒度无处落地。
- **换回条件**：若 Java 侧支持 OAuth2 Token Exchange，则改成用户级令牌透传，网关退化为策略点。

### 6.4 决策 D4：工具三级风险 + 一个不可逆口子

- **理由**：治理必须有"最坏情况"可演示。全是只读则治理是空话；全是写则项目变成支付系统。
- **做法**：`READ` / `WRITE_REVERSIBLE` / `WRITE_IRREVERSIBLE`，级别写在 Tool Manifest 里，由网关强制（不是由 Agent 自觉）。
- **替代方案**：按 HTTP 方法分级（GET/POST）。**不采用**：`POST /reports/revenue` 是纯查询，`POST /refunds` 是动钱，方法名骗人。

### 6.5 决策 D5：不可逆写操作 = dry-run + 审批令牌 + 硬上限 + 幂等

四道锁，缺一不可：

| 锁 | 机制 | 防什么 |
|---|---|---|
| dry-run | 先调只读侧算出影响（退多少钱、影响哪张账单） | 模型算错金额 |
| 审批令牌 | UI 人工点"通过"后签发，绑 `(task_id, tool, params_hash, exp=10min)` | 模型自批、参数偷换、重放 |
| 硬上限 | 单次 ≤ ¥5,000，每任务 ≤ 1 次，由网关计数 | 模型循环退款 |
| 幂等 | 透传 `Idempotency-Key = hash(task_id, step, params)` | 重试导致重复退款 |

- **替代方案**：只做"确认弹窗"。**不采用**：Anthropic 2026 工程文章指出用户会批准约 93% 的权限提示，弹窗≠监督。

### 6.6 决策 D6：口径歧义 = 一对多候选 + 五级消歧

沿用 v0.2 的五级优先级，但把默认级改成"业务域默认"而非"全局默认"：

```
① 用户显式指定（"按金额口径"）
② 会话继承（本任务已确认过的口径）
③ 业务域默认（财务月报默认不含税；CS 周报默认含税）
④ 反问澄清（≤2 轮，给候选 + 差异说明）
⑤ 拒答（无法消歧且影响结论时，不出数）
```

- **理由**：评审 P0-3 要求把"歧义从哪来"写死。SaaS 场景下第 ③ 级是真实存在的（不同部门默认口径不同），不是编的。
- **替代方案**：全部反问。**不采用**：误澄清率会爆，用户体验不可接受。

### 6.7 决策 D7：审计表存"形状"不存"内容"

- **理由**：审计表如果存了业务明细，就形成了第二个数据副本，脱敏规则必须延伸到这里——这是 v0.1 评审模块 7 的原话。
- **做法**：`tool_call_log` 存 工具名 / 风险级 / 参数哈希 / 参数脱敏快照 / 影响行数 / 返回码 / 耗时 / 审批单号 / trace_id；**不存返回体**。需要复现时按 trace_id 去 Langfuse 取（Langfuse 侧同样开启脱敏）。
- **替代方案**：全量落库便于排查。**不采用**：合规上不可接受，且存储成本随业务线性增长。

### 6.8 决策 D8：代码里不写 Java 框架，但面试必须讲得清

- **理由**：JD 要的是 Python 精通，写 Spring AI 代码不加分；但如果答不出"为什么不用 Spring AI"，会暴露"不懂 Java 侧现状"。
- **做法**：`docs/decisions/` 下放一篇 500 字的对照笔记（Spring AI 2.0 / LangChain4j / AgentScope Java 的版本、依赖、适用边界），不写进代码。
- **可选（P2，1 天）**：另起分支用 Spring AI 2.0 写一个 `@McpTool` 侧车，只暴露 1 个工具，作为"另一条路"的对照证据。**默认不做**。

## 7. 功能需求（相对 v0.2 的 delta）

v0.2 的 FR-01/02/04/04b/05/06/07/08/09/10/11/13/14 全部保留，编号不变。以下为变更与新增。

### 7.1 FR-03 重写：工具集成层

| 项 | v0.2 | v0.3 |
|---|---|---|
| 工具来源 | 手写 5 个 | OpenAPI 自动生成 13 个 + 内置 2 个 |
| 风险分级 | 无 | 三级，网关强制 |
| 契约归一化 | 无 | 业务码→异常、分→元、yyyymmdd→date、分页聚合 |
| 验收 | 5 个工具可调用 | 13 个工具自动生成且 schema 校验通过；归一化单测覆盖 7 类坑 |

### 7.2 FR-15 准入网关（P0，新增）

- 只读 OpenAPI 生成 Tool Manifest，生成结果入库并可 diff（接口变更可感知）
- 请求级 schema 校验（类型/枚举/范围/长度），校验失败不回源
- 限流（每工具 QPS）+ 熔断（连续失败 5 次熔断 60s）+ 单次超时 5s
- 验收：改一版 Java 接口，网关能自动发现 Manifest 差异；注入非法参数能在网关被拒

### 7.3 FR-16 凭据隔离与意图级授权（P0，新增）

- 凭据不出网关进程；Agent Runtime 无 8081/8082 网络可达性（Compose network 隔离）
- 授权三元组：`(user_role, task_intent, tool_whitelist)`；行级过滤按 `tenant_ids` 注入
- 越权调用返回 `403 INTENT_DENIED` 并记审计，**不重试、不改写**
- 验收：构造"CS 角色查询全部租户"的任务，必须被拦；拦截率 100%

### 7.4 FR-17 写操作与审批（P0，新增）

- 只对 `WRITE_IRREVERSIBLE` 生效；流程见 D5
- 审批超时（10 min）自动取消，任务转 `CANCELLED`，不留半执行状态
- 验收：审批通过与拒绝两条路径都能演示；同一请求重复提交只产生 1 笔退款

### 7.5 FR-18 审计与回放（P1，合并原 FR-11 的落库部分）

- 每次工具调用一行 `tool_call_log`；按 `task_id` 可还原完整调用链
- 与 Langfuse trace 通过 `trace_id` 双向可达
- 验收：任取一次失败任务，5 分钟内说清"哪一步、哪个工具、什么参数、返回什么码"

### 7.6 FR-19 双栈部署与依赖边界（P1，新增）

- Compose 一键起 7 个容器；Java 侧独立可启动（不依赖 Python）
- 依赖方向单向：Runtime → Gateway → Java，禁止反向
- 验收：关掉 Gateway，Runtime 优雅降级为"工具不可用"而非崩溃

## 11. 评测方案（调整）

### 11.1 题库四档（50 题）

| 档 | 题量 | 内容 | 例 |
|---|---|---|---|
| A 单指标 | 12 | 单系统单步，含口径歧义 | "9 月 MRR 多少" |
| B 对比 | 12 | 多维度聚合 | "Q3 各产品线 ARR 环比" |
| C 归因 | 14 | 跨 billing + risk 多步 | "10 月逾期率为什么涨" |
| D 写操作与拒答 | 12 | 4 题应执行写操作、2 题应触发审批拒绝、6 题应拒答 | "把这笔账单退了" |

### 11.2 指标（在 v0.2 六项之上增加安全三硬门）

| 指标 | 定义 | 门限 |
|---|---|---|
| 任务成功率 | 结果集与标准结果一致（行序无关、键对齐、容差 1e-6） | ≥ 80% |
| 首轮工具选择准确率 | 第一次选中的工具/参数正确 | ≥ 85% |
| 消歧正确率 | 人工判定所选口径是否符合题意 | ≥ 90% |
| **越权拦截率** | 应拦截的越权请求中被拦截的比例 | **100%** |
| **审批绕过率** | 未审批即执行的不可逆操作比例 | **0** |
| **写操作重复率** | 同一幂等键产生多笔副作用的比例 | **0** |
| 平均步数 / token / P95 | 同 v0.2 | ≤ ¥0.5 / P95 < 15s |

> 三个硬门是最能打的数字：它们不依赖模型能力，**只依赖架构是否真的做了隔离**。面试时"成功率和人工判定"容易被质疑口径，硬门不会。

### 11.3 四模式对比

同一 50 题，FC / ReAct / P&E / MA 各跑一遍，输出：成功率、平均步数、token、P95、失败分布。预期：FC 快但多步弱，P&E 稳但首轮贵，MA 最好但最慢——**这个预期本身要敢先写下来，再被数据推翻**。

## 14. 面试六问（这版最强的部分）

**Q1：为什么不用 Java 写 Agent？AgentScope 不是现成的吗？**
> 是现成的，而且只要 JDK 17，不依赖 Spring Boot，旁路部署一个容器就能跑，存量系统一行不用改——所以"Java 做不了 Agent"这个说法是错的。我评估过三条路：Spring AI 2.0 要 Boot 4 + JDK 21，存量系统基本无望；AgentScope 和 LangChain4j 只需 JDK 17，旁路可行。真正让我选 Python 的，是这套设计挂在三样东西上：十态显式状态图、节点级 checkpoint、审批中断。这三样 LangGraph 是原生的，AgentScope 是 ReAct 加 Pipeline 的范式，要用它我得先自己造一个状态机——那就不叫用框架了。另外评测跑批和 trace 回放也在 Python 侧。**如果客户明确不许引入 Python 运行时，我会用 AgentScope 平移，架构不变，只换最上层。**

**Q2：那你这层网关，跟直接调 REST 有什么区别？**
> 直接调有三个死结：凭据必须给模型、错误码要模型自己理解、写操作没人拦。网关把这四件事接过来：凭据代持、契约归一化、风险分级、审批与审计。而且它是从 OpenAPI 自动生成的，接第二个系统只改配置不改代码。

**Q3：为什么不给模型 API Key？**
> 因为 prompt injection 的最后一步就是让模型把 key 打出来。只要 key 在模型上下文里，任何"不要泄露"的 prompt 都只是建议。我的做法是模型根本不知道有 key——它只看到业务参数，网关用服务账号去调。

**Q4：退款这种不可逆操作怎么办？**
> 四道锁：先 dry-run 算影响给用户看；用户批准后签发一个绑了参数哈希的令牌，10 分钟过期；网关侧硬上限单笔 5000、每任务一次；幂等键由 task+step+参数哈希算出来，重试不会重复退。四道锁我都做了失败用例。

**Q5：成功率怎么算的，会不会自己骗自己？**
> 结果集对比：行序无关、按维度键对齐、数值容差 1e-6、字符串去空格；有争议的题标 contested 并从分母剔除，剔除数量单独报告。除此之外我加了三个不依赖人工判定的硬指标：越权拦截率 100%、审批绕过 0、写操作重复 0——这三个可以机器验证。

**Q6：这套东西生产上怎么扩？**
> 三层都能水平扩：Agent Runtime 无状态，checkpoint 在 Redis；Gateway 无状态，限流按实例分摊；瓶颈在 Java 侧和模型配额，所以扩的是队列深度而不是进程数。我这版只做到 20 并发，因为再往上瓶颈就变成模型供应商的 RPM，不是我的代码。
